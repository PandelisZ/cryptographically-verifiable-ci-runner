Choosing a store

Where vci keeps attestations, which store to pick, and how to set up each one. Since 2.8.0 there are four; git-meta stays the default, and a repository that configures nothing works as before.

vci run signs one attestation per unit that passed and stores it with the input manifest it refers to. vci plan reads them back, verifies them, and skips a unit when one proves its inputs unchanged. The attestation store is where those records live.

The store is never trusted. vci plan checks every attestation's signature against the base commit's .vci/allowed_signers and identities, and recomputes every input manifest's root, whichever store held it. A record that is forged, altered, replayed or deleted can only make a unit run. Write access to a store therefore matters for availability only: a writer can make CI slower by deleting records, and cannot make it skip a test it should run. Read access shows test ids, signer ids and input manifests (paths and content hashes), so give it to whoever may read the repository.

What fetch and push mean

  • git-meta writes to a local store. vci push publishes it on refs/meta/main, and vci fetch (or vci ci --fetch, as the action runs it) brings in what others pushed. On a busy repository that fetch and merge is the largest part of a plan: a median of 7.4 of 15 seconds on vex's Rails pull requests on 24 and 25 October 2026 (benchmarks).
  • SQLite has nothing to exchange. vci fetch says the sqlite store at … is local: nothing to fetch (N attestations stored), vci push says there is nothing to push, and both exit 0, so a workflow written for git-meta keeps working.
  • PostgreSQL and a libSQL server are shared. vci run writes to the server at once, and every reader sees it with no fetch. vci fetch and vci push say the store is shared and exit 0; the action's --fetch origin and --remote origin are ignored with a warning. vci fetch --remote and vci push --remote exit 2 on any store but git-meta.

On a shared store, vci ci stores nothing without --push. With git-meta nothing a CI job attests leaves it unless the job pushes, and the shared stores keep that rule. Without --push it signs, then prints:

vci: not storing 2 attestation(s): the libsql store is shared and vci ci was not given --push
vci ci: 2 unit(s) attested (not stored: the libsql store is shared and --push was not given)

The action passes --push only with signing-key or oidc (and push: true, the default), so in practice only the job you give CI's key stores anything. A developer's vci run always stores.

What each costs

Measured on synthetic stores on a laptop in October 2026; the benchmarks page has the tables and their caveats.

  • In a plan that skips 1,200 units, reading the attestations took 0.01 s from a SQLite file. From a libSQL server on the same machine, the first read took four requests and 0.42 to 0.57 s. A PostgreSQL plan of 1,200 units sends 14 statements.
  • vci run stored 1,200 attestations and manifests in one request (0.14 to 0.25 s) on libSQL, and in one transaction (0.20 to 0.76 s) in SQLite.
  • Across the internet each request adds a round trip. Turso's hosted service from a GitHub runner has not been measured yet.

Which store a repository uses

vci picks the store once per command, from the first of:

  1. VCI_STORE: git-meta, sqlite, postgres or libsql. Never a URL: a value with :// is refused and not printed.
  2. The scheme of VCI_STORE_URL: postgres:// or postgresql://, sqlite:, libsql://. An https:// URL needs VCI_STORE=libsql beside it.
  3. [store] backend in the working tree's vci.toml.
  4. The scheme of [store] url there.
  5. git-meta.

vci store info says which store was picked, where each setting came from, whether the store can be read, and how many attestations it holds. It never prints a password or a token, so its output is safe to paste into an issue or a chat:

$ vci store info
store: git-meta
location: .git/git-meta.sqlite (exchanged on refs/meta/main)
settings:
  backend: git-meta (the default)
  connect_timeout: 5s (the default)
  timeout: 30s (the default)
capabilities: shared writes no, lazy values yes, keeps hints yes
exchange: vci fetch and vci push, on refs/meta/main
status: ready
attestations: 4

It exits 0 when the store can be read, also before anything is stored, and 2 otherwise, after printing what it knows and the error. --format json gives the same as JSON. Run it first whenever a plan says reading attestations from ….

Keeping the store's credentials safe

A shared store has a credential: a Turso token, or a PostgreSQL password. vci handles it like this, and asks the same of you.

  • Never a credential in vci.toml. Every checkout carries it, a pull request's included. vci refuses a [store] url holding a password, a token, an authToken or a #fragment, without printing it. vci.toml may say where the server is ([store] url) and which command prints the credential ([store] token_command).
  • A token from the environment goes only to a URL from the environment. VCI_STORE_TOKEN with the URL from vci.toml is refused, because a pull request could change that URL to a server of its own and collect CI's token. CI sets both VCI_STORE_URL and VCI_STORE_TOKEN; a laptop sets neither.
  • Tests can still find the token. vci removes VCI_STORE_URL, VCI_STORE_TOKEN and VCI_STORE from its own environment as it starts and from every environment it builds for a test, probe, hook or token command. The environment a process started with stays readable to every process of the same user, though (/proc/<pid>/environ on Linux, ps eww on macOS), and so does the CI step's shell, which set the variables. vci cannot hide them there.
  • So a job that runs untrusted code gets a read-only token, or none. Only trusted jobs hold a token that can write: the default branch's, or pull requests from the same repository, whose authors could change the workflow and read its secrets anyway.
  • On your own machine, [store] url is as sensitive as token_command. The token the command prints goes to whatever [store] url names, and both come from the checkout. Review a change to either as you would a change to a test helper. In a checkout you have not reviewed, run vci with VCI_STORE=git-meta: it then ignores both and never runs the command.
  • Never print a token. Pipe it from turso db tokens create straight into gh secret set or your secrets manager, and never pass it as a command-line argument, where it lands in shell history and process listings. To see why a token command fails, run it with its standard output discarded (below).

Set up Turso (libSQL)

Turso hosts libSQL databases, so this is the shared store with no server to run. One database can hold many repositories, each in tables of its own. The steps below set up CI on GitHub Actions and the laptops and agents that attest.

  1. Install the Turso CLI and sign in

    brew install tursodatabase/tap/turso            # macOS
curl -sSfL https://get.tur.so/install.sh | bash   # Linux
turso auth login                                  # --headless on a machine without a browser

  2. Create the database

    turso db create vci       # add --group <name> if your organization has more than one group
turso db show vci --url   # libsql://vci-<organization>.<region>.turso.io

    The URL is not a secret: it says where the database is, and the token is what lets a client in. Create an ordinary database, without --tursodb: a TursoDB (MVCC) database's URL starts with turso://, which vci does not accept ($VCI_STORE_URL is not a libsql location, or, without VCI_STORE=libsql, a warning that git-meta ignores it).

  3. Decide who gets which token

    TokenMade withFor
    can writeturso db tokens create vcithe default branch's CI job, which stores what it attests; developers and agents whose vci run should store attestations
    read-onlyturso db tokens create vci --read-onlypull-request jobs, and any machine that only plans or runs code you have not reviewed. Its plans read the store; its writes are refused (libsql store refused to write: … the token may not write) and the tests' exit code is kept

    Tokens do not expire unless you say so: --expiration 90d sets a lifetime in days. An expired or revoked token makes the store unavailable, and every test then runs until you replace it. turso db tokens create prints the token alone on standard output, so pipe it to where it is kept (next step) instead of copying it from the screen.

  4. Store CI's values as GitHub secrets

    Create the environment vci-attest, limited to the default branch, if CI does not sign with a key of its own yet (attesting in CI shows how). Then, from a clone of the repository:

    turso db show vci --url | gh secret set VCI_STORE_URL
turso db tokens create vci --read-only | gh secret set VCI_STORE_TOKEN
turso db tokens create vci | gh secret set VCI_STORE_TOKEN --env vci-attest

    gh secret set reads the value from standard input when it has no --body, so the token never appears on screen or on a command line. A secret of an environment wins over a repository secret of the same name in the jobs that use that environment: pull-request jobs get the read-only token, and the main-branch job, which runs in vci-attest, gets the one that can write. Pull requests from forks get no secrets at all; their jobs cannot read the store and run every test.

  5. Give both jobs the two variables

    The same two lines in each job. The main-branch job also attests (signing-key, or oidc: true), and the action then runs vci ci --key … --push, which stores what it attested. On a shared store --push writes to the database, not to git, so that job needs no contents: write.

    name: test

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  # Pull requests: read the store, skip what is attested, store nothing.
  test:
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    env:
      VCI_STORE_URL: ${{ secrets.VCI_STORE_URL }}
      VCI_STORE_TOKEN: ${{ secrets.VCI_STORE_TOKEN }}   # the repository secret: read-only
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0      # the base commit, and the repository id the store's tables are named after
      # ...your toolchain steps...
      - uses: PandelisZ/cryptographically-verifiable-ci-runner@v2

  # Pushes to main: run what is not attested, attest it, store it.
  test-main:
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    environment: vci-attest
    env:
      VCI_STORE_URL: ${{ secrets.VCI_STORE_URL }}
      VCI_STORE_TOKEN: ${{ secrets.VCI_STORE_TOKEN }}   # vci-attest's secret: can write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      # ...your toolchain steps...
      - uses: PandelisZ/cryptographically-verifiable-ci-runner@v2
        with:
          signing-key: ${{ secrets.VCI_SIGNING_KEY }}   # or oidc: true (with permissions: id-token: write)

    Every step of a job can read its env, the install steps and the tests included, which is why the pull-request job's token is read-only. Without the action, run vci ci --base-ref "$BASE" --key "$KEY" --push in the main-branch job and leave out --push everywhere else.

  6. Point laptops and agents at it

    Commit a [store] table that names the database and the command that prints a token, so that nobody exports anything:

    [store]
backend = "libsql"
url = "libsql://vci-acme.aws-eu-west-1.turso.io"   # never a credential
token_command = ["com", "secrets", "get", "vci-store-token", "--org", "acme"]

    token_command is an array run directly, without a shell, or a string run with sh -c. It runs only when a command first reads the store, at most once per vci process, in the repository's top level, and must print the token alone on one line within 60 seconds. It cannot prompt, so sign in to the tool first. Some choices:

    # Composal: each read of the organization's secret is audited
token_command = ["com", "secrets", "get", "vci-store-token", "--org", "acme"]

# 1Password
token_command = ["op", "read", "op://Engineering/vci-store/credential"]

# a file: weaker (below). A string runs with sh -c, so ~ is expanded
token_command = "cat ~/.config/vci/store-token"

    A file is the weakest choice: the token sits on disk, readable by anything you run, never audited, and signing out does not revoke it. If you use one anyway, write it without showing it: mkdir -p ~/.config/vci && (umask 077; turso db tokens create vci > ~/.config/vci/store-token). In an array, ~ is not expanded: give the full path.

    In CI, VCI_STORE_URL and VCI_STORE_TOKEN win over [store], and the command never runs. A vci before 2.8.0 rejects a vci.toml with [store] and runs every test, so commit the table only once every runner and developer has 2.8.0 or later; until then, select the store through the environment.

  7. Check it

    vci store info

    Before anything is stored it says:

    store: libsql
location: libsql://vci-acme.aws-eu-west-1.turso.io namespace <repository id> (remote)
settings:
  backend: libsql (vci.toml [store])
  url: libsql://vci-acme.aws-eu-west-1.turso.io (vci.toml [store])
  mode: remote (vci.toml [store])
  token: (from token_command: com secrets get vci-store-token --org acme) (vci.toml [store])
  namespace: (the repository id) (the default)
  connect_timeout: 5s (the default)
  timeout: 30s (the default)
capabilities: shared writes yes, lazy values no, keeps hints yes
exchange: none (vci fetch and vci push have nothing to do)
status: absent: nothing is stored yet (the first `vci run` creates it)
attestations: 0

    In CI the token line says token: (set) ($VCI_STORE_TOKEN). The token itself is never printed.

  8. Expect the first runs to run everything

    The store starts empty. Until something is stored, a plan warns no attestations are available in the libsql store (the first `vci run` creates it) and every unit runs. The default branch's next full run fills it: no_skip_refs makes that run run everything, and with CI's key it attests every unit that passes and stores it. Developers' and agents' vci run add theirs. The first write with a token that can write creates the repository's tables; a read-only token cannot (libsql store is not set up: the first vci run with a token allowed to create tables creates them).

    Switching store copies nothing and invalidates nothing. The attestations on refs/meta/main stay there, unused, and each unit runs once more before the new store has it. There is no command that copies a store yet.

Replica mode

A machine that keeps its clone, such as a laptop or a self-hosted runner, can read a local copy of the database instead of asking the server for every plan:

[store.libsql]
replica = true   # or VCI_STORE_SYNC=replica in the environment

The copy is .git/vci-store.libsql. Each command that reads the store first syncs what changed since the last sync, in one request; with nothing new that took 0.01 to 0.04 s against a local server. Writes go to the server, then to the copy. A sync that fails prints vci: warning: cannot sync the libsql replica …; reading the replica as it is, and plans and runs go on with the copy as it was, which can only make units run. An ephemeral runner starts with no copy and syncs everything once, about what a remote plan reads anyway: 0.6 to 9.3 s for 7,201 records on a heavily loaded laptop.

Namespaces and shallow clones

Each repository's tables are named after its namespace: by default the repository id, its first commit (git rev-list --max-parents=0 HEAD). Forks and mirrors share it; unrelated repositories never do. A shallow clone cannot know its first commit, so there vci refuses the default:

attestation store: the libsql store keeps each repository's records under a namespace, by default the repository id (its first commit); this is a shallow clone, whose first commit is where the clone was cut: set $VCI_STORE_NAMESPACE (the same value wherever the store is shared)

Keep fetch-depth: 0 in CI, which vci needs for the base commit anyway, or set VCI_STORE_NAMESPACE to the same value everywhere. [store.libsql] namespace sets it in vci.toml.

When it does not work

A store that cannot be used fails open. vci plan prints a warning and running everything: reading attestations from libsql: …, every test runs, and nothing is skipped by mistake. vci run and vci ci run the tests, refuse to store each unit with the reason, and keep the tests' exit code. vci store info, vci fetch, vci push and vci prune exit 2 with the error.

Set up PostgreSQL

vci needs a database and three roles: one that creates the schema, one that writes for trusted CI, and one that reads.

  1. Create the database and the roles

    -- as an administrator
CREATE DATABASE ci;
CREATE ROLE vci_owner  LOGIN PASSWORD '...';   -- creates the schema
CREATE ROLE vci_writer LOGIN PASSWORD '...';   -- trusted CI: the default branch
CREATE ROLE vci_reader LOGIN PASSWORD '...';   -- pull-request jobs, and anyone who only plans
GRANT CREATE ON DATABASE ci TO vci_owner;

  2. Let the owner's first run create the schema

    The first write by a role allowed to create schema vci creates it. Until then reads find an empty store, and other roles get postgres store is not set up: the first vci run with a role allowed to create schema vci creates it. Run one vci run as vci_owner, then grant the others:

    GRANT USAGE ON SCHEMA vci TO vci_writer, vci_reader;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA vci TO vci_writer;
GRANT SELECT ON ALL TABLES IN SCHEMA vci TO vci_reader;
GRANT INSERT, UPDATE ON vci.memo, vci.flags TO vci_reader;   -- optional: the plan's hints

    A reader's vci run refuses each unit (postgres store refused to write: permission denied for table manifests) and keeps the tests' exit code. A job that runs untrusted code should get vci_reader without the optional grant, or no URL.

  3. Give CI the URL

    For PostgreSQL the password goes in the URL: postgres://vci_writer:<password>@db.example.com:5432/ci, percent-encoded where it holds @, /, ? or :. Store it the same way as Turso's token: a vci_reader URL as the repository secret VCI_STORE_URL, a vci_writer URL as the vci-attest environment's, and VCI_STORE_URL: ${{ secrets.VCI_STORE_URL }} in each job's env. VCI_STORE_TOKEN is not used.

  4. Point laptops at it

    [store]
url = "postgres://vci_writer@db.example.com/ci"   # a user, never a password
token_command = ["op", "read", "op://Engineering/vci-postgres/password"]

    The command prints the password. vci store info then shows password: (from token_command: …) and the URL with its user masked, postgres://***@db.example.com/ci.

Without sslmode, TLS is required, except for localhost, 127.0.0.1, ::1 and Unix sockets. Certificates are always verified, against the webpki roots and the CA file in ?sslrootcert=; a local server with a self-signed certificate needs sslrootcert or sslmode=disable. Back up with pg_dump -n vci. The full reference is in REFERENCE.md, PostgreSQL.

Set up SQLite

No server and no credential. Select it with the environment first, and in vci.toml once everyone has 2.8.0:

export VCI_STORE=sqlite
vci store info   # status: absent: nothing is stored yet (the first `vci run` creates it)
vci run          # creates .git/vci-store.sqlite
[store]
backend = "sqlite"

The file lives in the git common directory, so a clone's worktrees share it. Keep it off network file systems: SQLite's write-ahead log needs shared memory. To carry it between CI jobs, cache .git/vci-store.sqlite; each command checkpoints the log as it closes the store, so the one file holds everything. Jobs that run in parallel each save their own copy, and the last one saved wins.

For agents

The vci agent skill carries these rules for coding agents. In short: run vci store info to see which store a repository uses (its output is safe to paste); never print VCI_STORE_URL, VCI_STORE_TOKEN or what a token_command prints; never write a credential into vci.toml; debug a failing token_command with its standard output discarded; vci push on git-meta, and on a shared store let vci run store and leave vci ci --push to trusted CI jobs; and set secrets with gh secret set reading standard input.
