2.7.10

23 October 2026. Before a push, vci merges what other jobs published into its own metadata commit. That merge read every key of three trees (the merge base, this commit and the remote's tip, about 180,000 entries each on vex), merged them in memory and wrote the whole tree again: 18 s each push round of a full Rails run, though only a few thousand keys differed. When no path changed on both sides since the merge base, git now builds the merged tree (git merge-tree --write-tree), touching only the changed subtrees. git-meta's merge gives the same result there: a key only one side touched takes that side's state. When any path changed on both sides, or git cannot merge, git-meta's merge runs as before.

2.7.9

23 October 2026. 2.7.8's timings showed a vex plan spending 11.6 s finding the base manifests of the 2,035 manifests it reads, and its verdicts about 20 thread-seconds reading manifests. Each lookup of a manifest asked the store for the project row with that key without giving the project target's (empty) value, so SQLite could use only the first column of its index and scanned every project row, about 13,000 on vex, for each lookup. The lookup now names the empty target value, so the index finds the row directly (the old query still runs if that finds nothing). A merge of fetched metadata applies its deletion records in one transaction: git-meta applies each in a commit of its own, and the same plan's merge spent 8.4 s on 6,314 records and 2,212 deletions. vci runs git-meta's own statements, in the same order, on its connection to the store.

2.7.8

23 October 2026. A vex plan spent 23 s fetching the stored values it reads, about 5 of them downloading. To choose which attestations of each unit to fetch, it read the stored value of every candidate it had (through git cat-file), though the choice needs only the keys; then, to find the chosen ones' manifests, it read them all again. Choosing now reads no values, and finding the manifests reads only the chosen attestations. With VCI_TIMING, that step and a merge of fetched metadata (applying deletion records, recording the merge) report each of their parts.

2.7.7

23 October 2026. 2.7.5's record of the commit a store covers was lost at every merge of fetched metadata (which moves the local commit), so the push after a fetch still ran the full coverage check (4.6 s on vex). A merge of the tree's paths writes every entry the merged commit has that the local one did not into the store, as a row or a deletion record, and shares the rest with the local commit: a store that covered the local commit is recorded as covering the merged one.

2.7.6

23 October 2026. A vex pull request job's plan spent 24.5 s of its 109 s completing the fetched tip's tree: vci checked the tree with git ls-tree -r -d, which on git before 2.44 asks the promisor remote for any subtree that is not here, a request that fails (vci's promisor has no URL) after about 11 s, before and again after fetching the missing subtrees. The check now lists the missing trees with git rev-list --missing=print, which never asks, and fetches exactly those by id until none is missing.

2.7.5

23 October 2026. Every fetch checks that the store holds every value of the local metadata commit, or a deletion record for it, before git-meta serializes the store onto that commit (a new, emptied or linked worktree's store would otherwise delete values for everyone). The check reads every row of the store and every key of the commit: 2 to 8 s a fetch on vex's runners, 26 s in one job, every time finding nothing to restore. The store now records the commit it is known to cover, in its own SQLite file: after a full check, and after a serialization of a store that covered the previous commit. A fetch whose local commit is that one skips the check. Triggers on the store clear the record whenever a row or a deletion record is deleted, the only ways a store stops covering a commit, and a new or replaced store has no record, so those still get the full check.

2.7.4

23 October 2026. A vex pull request job that ran 50 of 2,051 Rails files (54 s of tests) took 334 s in all, about 170 of them in three push rounds of which each spent about 23 s merging the remote's metadata, whether 27 entries had changed or thousands. With VCI_TIMING, that merge now reports each part: the merge commit, listing the merged tree's keys, comparing the trees, reading the stored deletion records, fetching changed ones and marking the changed values.

2.7.3

23 October 2026. 2.7.1 skips a push onto a tip the remote has moved past and merges again instead. On a busy evening a vex job did that eight times in ten attempts: each round's fetch and merge takes 40 to 75 s, other jobs pushed more often than that, and after ten rounds, with two pushes in all, the job gave up (still rejected after 10 attempts). A round that merged again without pushing is no longer an attempt; after 30 of them vci pushes regardless. Ten attempts still means ten pushes.

2.7.2

22 October 2026. vex's master attest of its 2,033 Rails files printed "running 2033 test file(s)" and then nothing for 75 minutes, until the step's timeout ended it: a test process that never finished holds its slot, and the batch waits for every slot. The pull request jobs, about 1,000 files each, run in about 5 minutes. A file's process now has a limit, VCI_RAILS_FILE_TIMEOUT seconds (default 600, 0: none), in a batch's slot (a watchdog thread in the slot names a file still running after two minutes and stops it at the limit) and when it runs on its own (vci stops its process group). A stopped file fails, is not attested and is not run again on its own, where it would hang the same way; the batch's other files finish and are attested.

2.7.1

22 October 2026. Two costs in vex's Rails jobs, after a week in which a job with vci took a median 6.7 min against 4.2 without. A push the remote was going to reject took about 70 s, one that landed 7 s: when another job pushed after this one's fetch, git does not have the remote's new tip, cannot use it as the common base, and sends the whole metadata history before GitHub refuses the update. With two partitions and master's attest job finishing together, the jobs spent minutes in such attempts, and one ran out its time. Now vci asks the remote for its tip (one ls-remote) right before pushing and, when it moved, merges onto the new one at once. A job repacked the whole repository before pushing (17 to 19 s on git 2.43): it starts with a restored store's packs and adds one per value fetch, so it crossed the 16 packs at which vci merges them. That limit is now 24, still clear of the 32 pack slots gix opens a repository with.

2.7.0

22 October 2026. Three causes of vex's Rails jobs running everything. vci.toml was a file input of every unit, so any edit to it (a comment, a policy line, a new project) ran every unit of every project again: vex's two policy changes and their revert each did. A unit now records its project's settings as one external, vci:config: the project's directory, adapter and adapter settings, effective [env] and [[inputs]]. The policy is not part of it (it is read from the base commit when planning), nor are comments or other projects. Attestations made before 2.7.0 still verify as before (they hash the file); the ones made from now on stop depending on it. A project whose directory the checkout lacks (a branch from before the base's config added it) stopped vci plan, ci and run with "does not exist" and ran everything of every project; it is now left out with a warning. A store restored from a CI cache whose local metadata commit names trees the cache lacks failed every fetch and push (vex, Oct 21-22: 40 jobs in a row, could not fetch <tree> from promisor remote, so no pull request attestation landed for 18 hours and every run ran everything): a fetch now first fetches the local commit's missing trees by id from the remote, which has them once that commit was pushed.

2.6.5

20 October 2026. The cause of the push failures 2.6.3 and 2.6.4 chased. vex's CI pushes over https, and git's https helper always builds a thin pack: it does not accept the thin option, so git push --no-thin is ignored there (it applies over ssh and to local remotes, which is why no copy of the failure reproduced). A thin pack's delta search takes, for each path the push modifies, the remote tip's object at that path as a base, and pack-objects first fetches every such base the clone lacks, from the promisor, which vci's has no URL for, and stops on the first. A full run rewrites a few thousand deletion records the tip already held, records other jobs wrote and this blobless clone never downloaded: each attempt died on the next one in path order, the fallback fetched that one, and ten attempts went by. A copy of a failing CI job's object store reproduces it on git 2.43 with pack-objects --thin and passes without it. Now the tip's blobs at every path the push modifies are fetched with what the push sends, in one batch, before git builds the pack.

2.6.4

20 October 2026. Two findings from vex's first runs with rails_autoload_lookups. Checking a unit's inputs took 1,061 thread-seconds a job (22 to 28 before): every name a test looked up was compared with every child of every autoload directory, for each unit. The children are now listed and normalized once per manifest into one index, and each name is one lookup; the hashes are the same as before, so attestations made with 2.6.x still match. 2.6.3 did not make the pushes go through: git's own listing of what the pack needs (rev-list --not <tip>) found nothing missing, yet git push still asked for a deletion record the tip holds, as in 2.1.17's sparse-walk failures (that walk is still off). The same steps on git 2.43, against a copy of vex's metadata and with full code clones, push fine. A push that fails this way now also reports what the remote says its tip is, whether that commit is here, whether it is the tip this round merged onto and an ancestor of the pushed commit, and how many objects git would send against it; and with VCI_TIMING every failed attempt's diagnosis is printed (it was kept only for the last).

2.6.3

20 October 2026. The first vex pull request run after its policy changed (every Rails test ran again, as the environment lists changed) could not publish: both jobs failed ten push attempts, about ten minutes each, every attempt on another deletion record of an input manifest (could not fetch <blob> from promisor remote), records the remote's tip already held and this clone had never downloaded. On the first such failure vci fetched the deletion records of the pushed tree it lacked (2.2.9); that did not make the push go through, and every later attempt replaced one record with a new one. Now the first such failure fetches every object the pack needs that the clone lacks, as git itself lists them (git rev-list --objects --missing=print <pushed> --not <tip>, which never fetches), by id, in batches, until none is missing, and tries again. The diagnosis of an unreadable object no longer runs git cat-file -t, which on git before 2.44 asked the promisor for it: 18 s each attempt.

2.6.2

20 October 2026. A bug report from a laptop: vci plan printed its first timings and then nothing for 20 minutes, starting a new git cat-file --batch every few seconds, each living about 3 s; on 2.1.18 a vci push did the same for 46 minutes while holding .git/git-meta.vci-exchange.lock, so every other worktree's vci queued behind it. The repository had 1.88 million objects in 590 MB of packs, about 255 worktrees on one .git, git 2.39, and some interrupted fetches and a git fetch --refetch of refs/meta/main behind it. The store had values whose blobs the object database no longer held. vci reads stored values through one git cat-file --batch and started a new one after any error, also after git had only answered "missing". Git before 2.44 is worse: asked about an object the clone lacks, it tries the promisor remote, which vci's has no URL for, and exits. Every start reads the pack indexes (about 3 s there), once per missing value. Now "missing" keeps the process, and once a process has died, vci finds which stored values the object database holds with one git rev-list --missing=print (which never fetches, on any git) and fails the others at once, without starting git cat-file. Their units run (a value that cannot be read never skips anything). Reads of several values at once ask only for those present. 2.6.1 was built but never published (GitHub cancelled its macOS x86 build while it waited for a runner); 2.6.2 carries its change.

2.6.1

20 October 2026. 2.6.0's rails_autoload_lookups left one way of asking for a constant unseen: defined?(Constant), which Ruby answers without any method vci can hook. vex's own code asks that 26 times, among them defined?(::Agent::Swarms::LandingHolds), a check for a class a later change may add: with 2.6.0, adding it would not have run the tests whose behaviour it changes. The constant paths after defined? in every repository Ruby file a test loaded now count as names it looked up (each file read once per run). What remains unseen is a gem's own code asking that about an application constant.

2.6.0

20 October 2026. Of 38 recent vex pull request runs, 27 ran every Rails test. In 22 of them the first input that differed was the listing of an autoload directory (app/filters/api/v1, app/resources, app/models): Zeitwerk lists those directories while the application boots, so every test's attestation names them, and any file added there (by the change, or on master since the attestations were made) runs everything again. With rails_autoload_lookups = true in the base commit's [policy], such a listing is no longer an input. vci records instead the constant names each test's process looked up without loading them: a miss (const_missing, which a reference, const_get and constantize reach), and const_defined? answering false, or true for an autoload not loaded yet. A test then runs again only when an autoload directory gains, loses or renames a file or directory of one of those names. Names compare without case or underscores, in every autoload directory, whatever namespace asked, so a lookup from inside a controller that would find a new top-level model counts. A namespace whose constants are enumerated keeps its listings. In the test app, a new model no test asked for runs nothing again, and one a test asked const_defined? about runs that test, alone. It stays opt-in because Ruby answers defined?(Constant) without any method vci can hook: a test that asks that way may pass without having seen a constant a new file defines. The base commit's policy must allow it for a plan to accept such attestations.

2.5.0

20 October 2026. Until now, how long vci's steps take was printed only when VCI_TIMING was set, and only to that run's terminal: a slow run on a laptop (an agent's vci run "validating collected inputs before signing") left nothing to look at afterwards, and comparing runs meant reading CI logs one by one. Every vci command now appends one JSON line to <git common dir>/vci-metrics.jsonl: its version, command, flag names (never their values), exit code, duration, the machine (OS, architecture, CPUs, CI or not) and every step it times (the lines VCI_TIMING prints: the plan's fetches and verdicts, the Rails batch, checking, signing and storing, supersession, each part of a push, any git command over 2 s). vci metrics gives each step's median, 95th percentile and maximum over the last 50 commands (--last N, --command run, --format json). In GitHub Actions, vci ci also adds its slowest steps to the job's summary page. VCI_METRICS=<file> writes the log elsewhere and VCI_METRICS=0 writes nothing; the log keeps about its last 4 MB.

2.4.1

20 October 2026. 2.4.0 on a full vex run: the two jobs' test batches took 218 and 187 s instead of 251 and 194. On the same run, storing 1,008 units one at a time took 35.8 s on one runner and 9.6 s on the other. git-meta opens the store with synchronous=NORMAL, safe with its write-ahead log; vci's own connection, which stamps each write after it is committed, used SQLite's default, which syncs the disk on every commit. 2.4.0

20 October 2026. 2.3.9 on a full vex run: the plan took 31 s instead of 38 to 42, with no repack, and the jobs took 5.7 and 7.0 min. What separates the two jobs is their share of the tests: 194 s of batch against 251 s. --partition gave each unit the partition its test id hashes to, and with the durations vex's attestations record, that split gave the two Rails jobs 2,762 and 3,231 s of tests. A project whose units are all files is now split by size: every unit it lists, skipped or not, largest file first, goes to the partition with the fewest bytes so far. Ties go to the lowest partition, then the smaller test id. On the same files that gives 3,047 and 2,946 s; the recorded durations themselves would give 2,996 each. A split by recorded duration would not be safe: a job run again after the others pushed their attestations could see other durations and leave files to no job. File sizes and the listing come from the checkout, so every job agrees, whatever its plan skips. Rails: slots

A batch of Rails files now runs W at a time when the project runs its tests in Rails' parallel worker processes (parallelize in test_helper.rb). 2.0.0

17 October 2026. Four changes: what a fetch downloads, how CI can sign, one suite split over N CI jobs, and Rails runs that boot once. The major version is for the first: once 2.0 has fetched into a clone, vci 1.x cannot fetch or push there without a refetch (see upgrading).

A fetch downloads keys, not values

Every CI job's fetch downloaded the whole metadata ref, every value of every project, although a plan reads a few hundred of them. On vex that was 1.4 GB per job until vci prune --superseded && vci push --rewrite-history (1.8.2) dropped the old versions; what was left, about 40 MB, grew again with every attestation. vci fetch (and the action, and --fetch) now fetches refs/meta/main blobless: the commits and the tip's trees, whose paths are the keys, and none of the values. The store gets a row per key, a value not downloaded being a git-meta promised row, and the values are fetched when something reads them, in one git fetch of blob ids per batch: vci plan, vci ci and vci explain fetch the attestations of the units they verify, then the input manifests those reference; vci verify fetches the one manifest it reads, vci run the attestations of the units it supersedes, and vci prune every attestation. Merges work from paths and blob ids, with git-meta's results, and a push sends only what the clone wrote. A value that cannot be fetched (offline) makes its unit run, and vci explain says value not fetched: run `vci fetch` online.

Measured on a local copy of vex's metadata remote (4,540 entries, 1,257 values, 38.6 MiB packed, 24 commits), fetched into a fresh depth-1 clone of vex. 1.9.2's vci fetch downloaded 40.6 MB in 5.5 s; 2.0's downloads 1.8 MB in 1.0 s. A plan of one project (vex-web) then fetched 571 attestations and 50 manifests, 1.4 MB in two requests taking 0.5 s, and one of another project (rust) 157 attestations and 17 manifests, 1.5 MB. Fetch and both plans came to 4.7 MB instead of 40.6 MB, with 462 values never downloaded. 1.9.2's plan of vex-web took 1.1 s with everything already downloaded; 2.0's takes 1.0 to 1.4 s, the downloads included. Both versions printed identical plans, file for file. Every unit ran in both: that machine's toolchains differ from CI's, so this measures bytes and time, not skips. On a later copy of the same store (6,006 entries, 85 commits) the fetch is 2.1 MB, of which the 84 earlier commits are 36 KB: a fresh clone's download now grows with the number of keys, not with the size of the values or the length of the history.

What it changes in a repository: git accepts objects left out of a fetch only with a promisor remote configured, and asks that remote for anything it misses, code included. vci never makes the metadata remote one. It configures remote.vci-no-lazy-fetch, a promisor remote without a URL (it shows in git remote), so git gc and git fsck accept the values left out and a lookup of a missing object fails at once, as before, instead of downloading it with its history. The repository is never made shallow. Pushes send packs that are not thin, and vci push --rewrite-history fetches every value first. The remote must serve partial clones (uploadpack.allowFilter, as GitHub does); one that ignores the filter sends every value, as before. Details: the reference's "What a blobless metadata fetch changes in the repository".

Keyless attestation with the job's OIDC token

For CI to attest its own runs it needed an SSH private key, stored as a secret only main's job can read, rotated by hand, and readable by every process of that job. vci ci --oidc (the action's oidc: true, in a job with permissions: id-token: write) signs without one, the way npm publish --provenance and actions/attest do: an ephemeral P-256 key held in memory, a ten-minute certificate from Sigstore's Fulcio for the job's OIDC token, and an RFC 3161 timestamp per attestation. It uses GitHub's Sigstore instance (fulcio.githubapp.com, timestamp.githubapp.com) for public and private repositories alike, so no public log names every test unit; --oidc=public-good uses sigstore.dev's. Trust is .vci/identities.toml on the base branch: each [[identity]] names a principal and the claims a certificate must carry (issuer, repository, workflow file, ref, and optionally event, environment and runner type, as globs). A matching principal counts exactly like an allowed_signers one in no_skip_refs_except and attest_on_any_ref, and vci ci --oidc refuses to attest off main on the same terms as --key. Verification is offline, against the Sigstore trust root committed as .vci/sigstore-trusted-root.json (what gh attestation trusted-root prints): the certificate chains to it, a trusted timestamp puts the signature inside the certificate's ten minutes, its repository and workflow are on the issuer's host, and its identity matches an entry. No transparency log is checked. Any failure makes the unit run, and vci explain names the check. Main's runs and pull requests' runs of one workflow are separate signers in the store, so neither replaces the other's attestations. vci init --oidc writes both files; vci verify takes --identities and --trusted-root. Laptops keep SSH keys, and both kinds of attestation share the store and the policy.

First run on this repository's CI, on a pull request: a job with only permissions: id-token: write and no secret attested the 21 demo units (pytest, Go, Cargo, Rails, RSpec) with vci run --oidc, about 0.1 s per signature, and vci plan then skipped all 21 on those attestations (with the pull request's own commit as the base, for the demonstration; the workflow now checks the trust files from the base branch, and that version has not run yet). An envelope from that run is a test fixture, verified offline against GitHub's trust root.

One suite over N CI jobs

vci ci --partition I/N (the action's partition: I/N) runs only partition I's share of what the plan runs, so a suite that a runner used to split (cargo nextest run --partition hash:I/N) can run through vci ci --key --push and be attested. A unit belongs to the partition the first 8 bytes of its storage key (BLAKE3 of the test id) fall in, modulo N: the same in every job and on every machine, whatever the plan's order or what the other jobs do, so every unit runs in exactly one partition, and what the plan skips is skipped in all of them. Each job attests and publishes its own share; the next plan skips every partition's units. A project a job cannot list (cargo missing on one runner, a transient cargo metadata failure) runs whole in that job with a ::warning, since the job cannot know whether another listed it: such units may run in more than one job, never in none. The exit code is the partition's tests'; the audit log's ran holds its units and partition is {index, count, units, total, unlisted}. --partition 1/1 is vci ci without the flag. Partitions balance unit counts, not durations, and a cargo unit is a whole test target.

Proven by three clones running vci ci --fetch origin --partition I/3 --key --push at once on the node-test and cargo fixtures: the attested sets are disjoint, their union is the plan's run set, a fresh clone's plan then skips everything; and by a review's six-job run on a three-project repository (24 of 25 units attested, the deliberately failing file the one left). The review found that a job that could not list a project skipped it with exit 0 while partition 1 ran only its own share, so those units ran nowhere; fixed as above.

Rails: several files, one boot, attested per file

vci run and vci ci --key of several Rails or RSpec files used to start one process per file: on vex-api, 2,400 boots, hours, so CI never attested Rails. Now one process per runner boots the application once, then forks one process per file, one at a time; each runs only its own file and writes its own output, so every file's attestation records what a run of that file on its own records, with its own result and exit status. Before each fork the boot's database connections are closed (as Rails' parallelize does); what the batch cannot run that way (a group whose helper fails in the boot, a file's process without output, a runner vci does not recognise) runs again one process per file, and vci run says so. VCI_RAILS_PER_FILE=1 keeps one process per file; the collector's output and version (0.5.0) are unchanged, so existing Rails attestations stay valid. The collector also no longer breaks when a test stubs ENV[] or File.read by alias, as vex-api's Object#stub does (every later call recursed until the stack overflowed, so such a file was never attested).

1.3.0

15 October 2026. Two things people asked for after the first deployments: CI should not re-run on commit B what it already ran on commit A, and an attestation made on a Mac should count on a Linux runner.

CI attests its own runs

vci ci can now sign what it runs. With --key, the units the plan says to run go through the same path as vci run: inputs recorded, attestation signed and stored. --push publishes them, --ttl sets their lifetime and --remote the destination. On a ref where policy runs everything, such as main, every unit is attested, so the next commit skips each unit whose inputs did not change. A commit that only touches the docs plans everything as SKIP and vci ci finishes without starting a test runner.

The new policy key no_skip_refs_except = ["github-actions"] names the allowed_signers principals whose attestations may still skip on a no_skip_refs ref. Any other signer is refused there by name, so a laptop attestation never skips on main; only the CI key does. Off those refs a key listed there attests nothing, so a pull request run cannot sign with the main key even if a workflow passes it.

The GitHub Action gains signing-key, ttl and push inputs and an attested output. The key must come from a GitHub Environment restricted to the default branch, never a repository secret: every process of the job can read it, and a same-repository pull request runs its own copy of the workflow. The job needs permissions: contents: write to push. Attesting in CI has the setup and the two-job workflow.

The audit log gains attested, pushed, notAttested and attestErrors. A project that cannot run with the collectors runs alone without attesting; the others are still attested, nothing runs twice, and the exit code covers every test.

Proven on this repository's own main branch: the first push attested 13 units, the next push, which changed one pytest module, ran only that test, and a docs-only push ran nothing for pytest, Go and Rust.

Attest on macOS, skip on Linux

policy.libraries = "any" (default "exact"; per project, or per glob in [[policy.platform_overrides]]) makes an attestation made on one platform count on another when the libraries differ only by build. Native libraries opened through FFI, such as Active Storage's libvips, match by library name instead of file name and hash: libvips.42.dylib on a Mac matches libvips.so.42 on Ubuntu, provided libvips is loaded on both sides. The SQLite, libyaml and time-zone data versions of the Rails toolchain, and SQLite and OpenSSL of the pytest toolchain, are not compared. Whether each is loaded still is, so a Python built without _sqlite3 never satisfies an attestation that used it. Ruby and Python versions, the bundle, the environment and every input are compared exactly as before. vci explain prints the policy and each difference it accepted. Nothing changes on the attestation side, so existing attestations verify under the new policy.

Fixed

  • A bundle installed inside the repository, as ruby/setup-ruby's bundler-cache: true does at vendor/bundle, refused every Rails and RSpec file with ruby:read-outside-bundle. Bundler's install directory is now a gem root like any other: nothing under it is a repository input, its gems are externals by version, and RubyGems' and Bundler's own bookkeeping there is not recorded. Still refused, now for bundles anywhere: loading, reading, listing or evaluating anything under a gem root that is not a gem of the bundle, including through Gem.read_binary, Bundler.read_file, Gem::Util.glob_files_in_dir and Gem::Specification.load, and a test's own check of vendor/bundle or of a gem's real path. Require shadowing probes skip gem directories, which makes a Rails file about a third faster to attest.
  • Under libraries = "exact", a native library loaded under another file name is reported as such, with a note that "any" would match it by name.

Upgrade notes. The Ruby collector is now 0.4.2, so existing Rails and RSpec attestations run once more in CI. The @v1 action before this version ignores the signing-key input and rejects no_skip_refs_except and libraries in a base policy, so everything runs; move to 1.3.0 before adding either key.

RSpec support in the Rails adapter: spec files run one per process through rspec --options .rspec, with the repository's .rspec as an input and ~/.rspec, the XDG options file and .rspec-local never read. Pending, skipped and focus-filtered examples are refused. Fifteen issues from the adversarial pass were fixed, including a non-zero exit after RSpec finished being ignored and a stub of File.directory? blinding the collector.

0.2.0

1 October 2026. Attestation storage moved from custom refs/attest/* refs to git-meta metadata on refs/meta/main, attached to the path of the test unit and readable with git meta get; the git-meta library is built into vci, so CI needs nothing extra. The Rails (Minitest) adapter arrived with a Ruby collector, a fresh SQLite database per file, and the rails_allow_db waiver for database servers.

0.1.0 and 0.1.1

28 September 2026. The first releases: Vitest, pytest, Go and Cargo adapters, each adversarially tested; the composite GitHub Action with prebuilt, checksum-pinned binaries for Linux and macOS on x86_64 and arm64; Turborepo-style environment policy. 0.1.1 relicensed the project and bumped the binaries.
