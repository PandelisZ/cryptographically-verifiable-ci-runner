2.1.17

19 October 2026. Both vex master attest jobs after 2.1.15 failed to publish their 2,012 attestations: ten push attempts each, every one failing on the same object, a manifest the tip's tree held (a pull request job had just pushed the identical manifest) and the clone had never fetched. The pre-push check of 2.1.10, which walks the objects of the pushed commit minus the tip's with git rev-list, found nothing missing each time, and 2.1.16's checks of the tip's tree and the changed blobs passed. The difference is in git: a push builds its pack with pack-objects --sparse (the default since git 2.27), a walk along the paths that introduce new objects which git documents as able to pack extra objects for some tree shapes, while rev-list walks fully. On a 100,000-entry metadata tree rebuilt around 2,000 new manifests and 2,000 deletion records, the sparse walk missed that the tip reached that manifest and tried to pack it. A push now packs with pack.useSparse=false, the same walk as the check, which takes about a second on vex's tree; and a push that still fails on an unreadable object puts its diagnosis (the object, whether it is readable here, whether the tip's tree is complete, how many objects are missing) in the error, where 2.1.16 had it only in notes that a failed push never printed. Reproductions that pushed fine throughout, for the record: two blobless clones superseding the same attestation; the same over a full local mirror of vex's store, with the pull request key, on macOS git 2.56 and Ubuntu 24.04 git 2.43 with vci prune between attest and push; identical manifests under two signers.

2.1.16

19 October 2026. The three pushes of 2.1.13 that failed on could not fetch ... from promisor remote now have a timeline. Each unreadable object was a deletion record a concurrent job had written (its stamp is the other job's supersession time), pushed a minute before the failing job fetched: two jobs of two branches had re-attested the same files and each superseded the same older attestations. The merge put the other job's deletion record into the failing job's tree, which is correct, and that record is reachable from the tip, which git excludes from the pack by walking the tip's tree. Git stops that walk silently under a subtree it cannot read, so anything under it is packed, and the never-fetched record fails the push; the pre-push check of 2.1.10 uses the same walk and is blind the same way. The tip's tree was complete when fetched, so what made a subtree unreadable between fetch and push is still unproven (2.1.15 removed the gc --auto that ran there). A push now completes the tip's tree again right before git push, and finds the blobs the pack must send by comparing the two trees (git diff-tree) as well as by the walk, fetching what is missing. When a push still fails on an unreadable object, its note names the object, whether this clone can read it now, whether the tip's tree is complete, and how many objects of the pushed commit are missing with nothing excluded, so the next such failure is explained by its log.

2.1.15

19 October 2026. In the first hour of 2.1.13 on vex, two jobs of two runs could not publish the 1,000 attestations each had made, and the next run of each branch ran those files again. The first job's push failed in its fetch: the tree of metadata commit ... is incomplete after fetching it. The metadata tip's tree has 108,000 subtrees, and GitHub served the fetch of its id without 12 of them, on the runner and on a laptop alike, while serving each of the 12 when asked for by id. A tree fetch now asks git which subtrees are missing and fetches those by id, up to five rounds. The second job's push failed while git built the pack: could not fetch 42b438a7... from promisor remote, a deletion record the job itself had just written, which the pre-push check (2.1.10, the same traversal) had found present seconds earlier. The cause is not pinned (the fetch's gc --auto, detached and repacking the object database while the push read it, is the suspect); a push that fails this way now fetches and tries again, like one rejected for a moved tip, saying in its notes whether the tip had moved, and vci's metadata fetches no longer trigger gc --auto. A third failure showed on a laptop clone once the tree fetch was fixed: after a fetch of 10,000 values in parallel batches, every git-meta read failed with The slotmap turned out to be too small, because gix sizes its pack slots when a repository is opened (32 at least) and each git fetch had left a pack of its own (74 in that clone). A batched fetch now consolidates its packs (git repack --geometric=2 -d, as git-meta does after its own), 74 packs became 3, and the fetch went through. The store's tests push from a blobless clone while another writer lands in between.

2.1.13

19 October 2026. On vex's Rails jobs, with every file attested, the plan still took 41 s: 24 s fetching values, 12,308 attestation envelopes and 12,153 manifests (about six attestations per file are stored, from branches still alive) to check 2,036 candidates, one per file. Two causes. The three batches (envelopes, manifests, bases) each listed the store's promised rows and the whole local metadata tree, 12 s of the 24. And the plan fetched every candidate's manifest though it checks a unit's newest attestation first and reads another's only when that fails. VCI_TIMING=1 prints round 2: fetch N more manifest(s), check the units not skipped again. On a laptop against vex's store the fetch phase of a whole-repository plan went from 21 s to 4 s with the same verdicts; the store's tests fetch a chosen manifest first and the other in a later round, and the cargo end-to-end test attests an edit, reverts it, and checks a fresh clone's plan skips the unit through the second round.

2.1.8

2.1.7

19 October 2026. On vex, 13 of 2,021 Rails files could never be attested, so every job of every push booted Rails to run them (about 25 s a job) and planned "13 to run" forever: nine with a test skipped under CI, two benchmark files with no test outside a benchmark run, two that probe public/ under two spellings of an organization's slug. All three are now a policy decision instead of a refusal:

  • Minitest and RSpec report a skipped or pending test as a passed result with skips, as pytest does, so policy.ignore_taints = ["result:skipped"] waives it for them too (before it was a failed result, which nothing waived; without the waiver it is refused as before).

And the slot retry of 2.1.5 is proven on a real collision by an end-to-end test: two files leave rows in their slots' databases, a third fails in whichever slot takes it, runs again on its own, passes, and is attested with exit 0.

2.1.3

19 October 2026. The first Rails run with 2.1.2 on vex's runners: the plan's verdicts phase 9.5 s (1,124 to 1,247 s before), the four jobs 5 to 9 minutes for all 2,005 files (28 to 30 before, cancelled). Where the rest went, and what this release does about it:

  • Files run longest first. The jobs' Ruby phases were 142, 202, 329 and 377 s for about 500 files each at 16 slots, where the files' process times add up to 94 to 117 s a slot: the slots waited on a last file of 78, 106, 141 and 212 s taken near the end of the listing. vci run now hands the runner the units longest first, by the duration their newest stored attestation records (result.durationMs, any signer; units without one first, in the listing's order), so a batch, Vitest, pytest or node:test run that takes several at once ends with its short files. The lines, the summary and the store keep the listing's order.
  • A rebased pull request's earlier attestations are superseded. Nothing was superseded on the runners: the earlier pushes' commits were rebased away, and an attestation whose commit this clone did not have was kept ("nothing is concluded from a history that is not there"). A commit on no branch, remote-tracking branch or tag at all, or one a full (not shallow) clone does not have, can be checked out by no name: an attestation of that commit by the same signer with other inputs is now superseded, as one on an earlier commit of the line was. A shallow clone still concludes nothing. Without this, every push of a pull request added its 2,000 attestations and their manifests to the store for good.
  • The superseded ones are found in parallel. Finding them (reading and decoding the unit's earlier manifests) ran one unit at a time with the store writes: 26 to 46 s of a 36 to 58 s check-and-sign phase. It now runs on the checking threads; only the removal stays with the store writes.
  • VCI_TIMING=1 shows the push's parts (fetch and materialize the remote's metadata, check what the push sends, put the local metadata on top, git push): 31 to 58 s a job on the runners, with no line saying why.

2.1.1

19 October 2026. The first Rails pull request runs on vex's 16-core runners (vci 2.1.0) showed two costs that this Mac had not: the second run's plan spent 19 to 20 minutes in its verdicts phase for 2,004 candidates (5 seconds here), and the first run's check-and-sign phase ran at one unit a second (25 a second here). Both come from the shape of a Rails attestation on that application: 13,800 inputs a file, 10,000 of them Ruby's load-path probes (vex-api/lib/<feature>.rb, vex-api/vendor/<feature>.rb, .so, .bundle, absent, one per require per load-path directory ahead of the gem's), 1.9 MB a manifest.

  • The plan reads manifests in parallel. It read each candidate's manifest from the store behind one lock, with one git cat-file process, so sixteen verifying threads waited on one reader (a sampler showed the plan in mutexwait). Each verifying thread now has a reader of its own. On this Mac the same plan went from 44 s to 9.4 s.
  • Load-path probes fold into one listing. When fifty or more absent probes fall under one existing directory (the deepest one on the way to each probe), the collector records that directory's listing instead of the probes: a folded probe can only come to exist by a new name appearing in that listing, so this re-runs more, never less. Probes under a directory that holds one of the test files, that is git-ignored, written during the run, under a symlink or under vci's temp dirs stay as they are; without an answer from git check-ignore nothing is folded. On five vex-api model tests a manifest went from about 2,300 entries and 310 KB to about 460 and 60 KB (locally, lazy loading); the CI sample, 13,848 entries and 1.9 MB, folds to 3,875 and 517 KB, which projects vex's 5 GB store to about 1.4 GB. The plan skips the five files, re-runs them when a file is added under lib/ or vendor/, and skips them again once it is removed.
  • VCI_TIMING=1 shows every part. After the verdicts phase, the plan prints per project how many candidates were checked and rehashed and the thread-seconds spent on signatures, global inputs, manifest reads, decoding, case-collision checks, ignored children, rehashing, externals and env; vci run prints the same for its check, sign and store phase. These are what will say where a slow runner's time goes.

2.1.0

18 October 2026. What it took for CI to attest a Rails application the size of vex-api (2,000 test files, a seeded MySQL database, 16-core runners that run the suite in 5 minutes with Rails' parallel workers), measured on it throughout. Three costs, each removed; the arithmetic is in docs/notes-rails-rollout.md.

Rails: slots

A batch of Rails files now runs W at a time when the project runs its tests in Rails' parallel worker processes (parallelize in test_helper.rb). Each slot is set up exactly as Rails sets up a worker: the before-fork hooks once, then in each slot parallel_worker_id = i and every after-fork hook (Active Record creates and loads <database>_<i>, parallelize_setup runs, Oaken loads its seeds), and parallelize_teardown at the end. Each file still runs in a process of its own, forked from its slot, so its inputs, result and exit status are its own; it does not seed again, because the slot answers Minitest's should_parallelize? as a worker does. By decision, this is not deterministic at the database level: a file starts from its slot's database as the slot's earlier files left it, as in a Rails worker; the database's contents were never an input. W is VCI_RAILS_JOBS, else PARALLEL_WORKERS above 1, else VCI_JOBS or the CPU count, capped by parallelize(workers: n); workers: 1 or PARALLEL_WORKERS=1 keeps one file at a time, and so does a project without parallelize. Fail open throughout: a slot whose setup raises takes no file; a write to vci's temp directory outside a slot's own, even one undone before the batch ends, sends the group back to one process per file; a slot killed mid-batch hands its file back; each group starts from a clean temp directory. The boot's observations, identical for every file of a slot, are written once per slot instead of once per file: a file's output went from 3.5 s to 0.17 s, and the merged result is byte for byte what a one-file run writes (VCI_RAILS_SHARED_OUTPUT=0 turns it off).

Measured on vex-api: 50 files 1,433 s one at a time, 168 s in 8 slots, the same 47 attested; the 939-file application group in 8 slots, 32 minutes, where one process per file was about ten hours. An adversarial review of the first version found five ways a slot could leak into another's file; all are fixed with tests, the serious one being a temporary file one slot's test wrote and removed that another slot's test saw.

The plan reads the checkout once

vci plan rehashed every entry of every candidate's manifest and ran one git check-ignore per manifest per candidate: on vex-api's 1,992 files and 2,784 attestations, 513 to 613 seconds, growing with the store, paid twice per job. Now a path is observed once per plan and shared by every candidate of every file (vci_core::CheckoutCache), git is asked once per directory, the global manifest is captured once, files are verified in parallel (VCI_JOBS) in the listing's order, and each file's candidates are checked newest first. Measured: the verdicts phase 4.6 to 5.7 s warm, 10 s with the 8 GB store out of the page cache; the same verdict, reason and signer for all 1,992 files. The checkout must not change while a plan runs.

Units checked and signed in parallel

After the tests, vci run checked and signed units one after another, 1.23 s each on vex-api; sampling showed 95% of it in git check-ignore over every child of every listed directory, per unit, not hashing or ssh-keygen. Units are now checked and signed VCI_JOBS at a time, the checkout read once per run, git asked once per path; lines, summary, exit code and the store's keys are those of a one-at-a-time run. Measured: 939 units in 37.8 s (0.04 s a unit) instead of 1,154 s. Keyless signing is parallel too, its certificate renewal behind a lock.

Also

  • A test that captures ENV.method(:[]) and then stubs ENV[] no longer recurses into the collector's hook (SystemStackError): a redefinition of a hooked method in the hooked class is watched, and a hook re-entered from the stub through Method#call runs the original.
  • A child Ruby process a batch's test starts runs with no collector and prints nothing (it used to print VCI_OUT or VCI_TEST_ID not set to stderr, failing a test that expects it empty); the parent records the spawn as before. A child no longer ends the batch for every file at its exit, and a runner that execs Ruby again stays the batch.
  • A test file whose first statement requires another test file of the batch no longer makes its group drive the batch again.
  • The plan's "best failed" reason and a failed git check-ignore (a path in a submodule or beyond a symlink) give exactly the answers 2.0 gave, whatever the thread order.

2.0.0

17 October 2026. Four changes: what a fetch downloads, how CI can sign, one suite split over N CI jobs, and Rails runs that boot once. The major version is for the first: once 2.0 has fetched into a clone, vci 1.x cannot fetch or push there without a refetch (see upgrading).

A fetch downloads keys, not values

Every CI job's fetch downloaded the whole metadata ref, every value of every project, although a plan reads a few hundred of them. On vex that was 1.4 GB per job until vci prune --superseded && vci push --rewrite-history (1.8.2) dropped the old versions; what was left, about 40 MB, grew again with every attestation. vci fetch (and the action, and --fetch) now fetches refs/meta/main blobless: the commits and the tip's trees, whose paths are the keys, and none of the values. The store gets a row per key, a value not downloaded being a git-meta promised row, and the values are fetched when something reads them, in one git fetch of blob ids per batch: vci plan, vci ci and vci explain fetch the attestations of the units they verify, then the input manifests those reference; vci verify fetches the one manifest it reads, vci run the attestations of the units it supersedes, and vci prune every attestation. Merges work from paths and blob ids, with git-meta's results, and a push sends only what the clone wrote. A value that cannot be fetched (offline) makes its unit run, and vci explain says value not fetched: run `vci fetch` online.

Measured on a local copy of vex's metadata remote (4,540 entries, 1,257 values, 38.6 MiB packed, 24 commits), fetched into a fresh depth-1 clone of vex. 1.9.2's vci fetch downloaded 40.6 MB in 5.5 s; 2.0's downloads 1.8 MB in 1.0 s. A plan of one project (vex-web) then fetched 571 attestations and 50 manifests, 1.4 MB in two requests taking 0.5 s, and one of another project (rust) 157 attestations and 17 manifests, 1.5 MB. Fetch and both plans came to 4.7 MB instead of 40.6 MB, with 462 values never downloaded. 1.9.2's plan of vex-web took 1.1 s with everything already downloaded; 2.0's takes 1.0 to 1.4 s, the downloads included. Both versions printed identical plans, file for file. Every unit ran in both: that machine's toolchains differ from CI's, so this measures bytes and time, not skips. On a later copy of the same store (6,006 entries, 85 commits) the fetch is 2.1 MB, of which the 84 earlier commits are 36 KB: a fresh clone's download now grows with the number of keys, not with the size of the values or the length of the history.

What it changes in a repository: git accepts objects left out of a fetch only with a promisor remote configured, and asks that remote for anything it misses, code included. vci never makes the metadata remote one. It configures remote.vci-no-lazy-fetch, a promisor remote without a URL (it shows in git remote), so git gc and git fsck accept the values left out and a lookup of a missing object fails at once, as before, instead of downloading it with its history. The repository is never made shallow. Pushes send packs that are not thin, and vci push --rewrite-history fetches every value first. The remote must serve partial clones (uploadpack.allowFilter, as GitHub does); one that ignores the filter sends every value, as before. Details: the reference's "What a blobless metadata fetch changes in the repository".

Keyless attestation with the job's OIDC token

For CI to attest its own runs it needed an SSH private key, stored as a secret only main's job can read, rotated by hand, and readable by every process of that job. vci ci --oidc (the action's oidc: true, in a job with permissions: id-token: write) signs without one, the way npm publish --provenance and actions/attest do: an ephemeral P-256 key held in memory, a ten-minute certificate from Sigstore's Fulcio for the job's OIDC token, and an RFC 3161 timestamp per attestation. It uses GitHub's Sigstore instance (fulcio.githubapp.com, timestamp.githubapp.com) for public and private repositories alike, so no public log names every test unit; --oidc=public-good uses sigstore.dev's. Trust is .vci/identities.toml on the base branch: each [[identity]] names a principal and the claims a certificate must carry (issuer, repository, workflow file, ref, and optionally event, environment and runner type, as globs). A matching principal counts exactly like an allowed_signers one in no_skip_refs_except and attest_on_any_ref, and vci ci --oidc refuses to attest off main on the same terms as --key. Verification is offline, against the Sigstore trust root committed as .vci/sigstore-trusted-root.json (what gh attestation trusted-root prints): the certificate chains to it, a trusted timestamp puts the signature inside the certificate's ten minutes, its repository and workflow are on the issuer's host, and its identity matches an entry. No transparency log is checked. Any failure makes the unit run, and vci explain names the check. Main's runs and pull requests' runs of one workflow are separate signers in the store, so neither replaces the other's attestations. vci init --oidc writes both files; vci verify takes --identities and --trusted-root. Laptops keep SSH keys, and both kinds of attestation share the store and the policy.

First run on this repository's CI, on a pull request: a job with only permissions: id-token: write and no secret attested the 21 demo units (pytest, Go, Cargo, Rails, RSpec) with vci run --oidc, about 0.1 s per signature, and vci plan then skipped all 21 on those attestations (with the pull request's own commit as the base, for the demonstration; the workflow now checks the trust files from the base branch, and that version has not run yet). An envelope from that run is a test fixture, verified offline against GitHub's trust root.

One suite over N CI jobs

vci ci --partition I/N (the action's partition: I/N) runs only partition I's share of what the plan runs, so a suite that a runner used to split (cargo nextest run --partition hash:I/N) can run through vci ci --key --push and be attested. A unit belongs to the partition the first 8 bytes of its storage key (BLAKE3 of the test id) fall in, modulo N: the same in every job and on every machine, whatever the plan's order or what the other jobs do, so every unit runs in exactly one partition, and what the plan skips is skipped in all of them. Each job attests and publishes its own share; the next plan skips every partition's units. A project a job cannot list (cargo missing on one runner, a transient cargo metadata failure) runs whole in that job with a ::warning, since the job cannot know whether another listed it: such units may run in more than one job, never in none. The exit code is the partition's tests'; the audit log's ran holds its units and partition is {index, count, units, total, unlisted}. --partition 1/1 is vci ci without the flag. Partitions balance unit counts, not durations, and a cargo unit is a whole test target.

Proven by three clones running vci ci --fetch origin --partition I/3 --key --push at once on the node-test and cargo fixtures: the attested sets are disjoint, their union is the plan's run set, a fresh clone's plan then skips everything; and by a review's six-job run on a three-project repository (24 of 25 units attested, the deliberately failing file the one left). The review found that a job that could not list a project skipped it with exit 0 while partition 1 ran only its own share, so those units ran nowhere; fixed as above.

Rails: several files, one boot, attested per file

vci run and vci ci --key of several Rails or RSpec files used to start one process per file: on vex-api, 2,400 boots, hours, so CI never attested Rails. Now one process per runner boots the application once, then forks one process per file, one at a time; each runs only its own file and writes its own output, so every file's attestation records what a run of that file on its own records, with its own result and exit status. Before each fork the boot's database connections are closed (as Rails' parallelize does); what the batch cannot run that way (a group whose helper fails in the boot, a file's process without output, a runner vci does not recognise) runs again one process per file, and vci run says so. VCI_RAILS_PER_FILE=1 keeps one process per file; the collector's output and version (0.5.0) are unchanged, so existing Rails attestations stay valid. The collector also no longer breaks when a test stubs ENV[] or File.read by alias, as vex-api's Object#stub does (every later call recursed until the stack overflowed, so such a file was never attested).

Measured on vex-api (macOS, Ruby 3.4.9, MySQL 8): 50 files of the application group took 1,110 s instead of 2,035 s one process per file, with the same 47 attested and the same 3 refused, and input roots equal to the files' own runs. What remains per file is vex-api's own reseeding of its database in each process's first test (Oaken's replant_seed, about 17 s a file): with that moved into the test helper (an experiment, a trade-off for vex to make), the same 50 files took 265 s. A first version ran every file in one process and attributed observations to files; review reproduced eight ways a file's attestation then differed from its own run (an inherited failing test counted for the parent's file, a monkey patch or shared examples at one file's top level making another pass, parallelize_me! threads mixing files, a memoized helper serving later files without an input, and more). Forking per file removes all of them by construction, and an e2e test runs twenty files covering each finding both ways and compares attestations entry for entry. Findings: docs/spike-rails.md.

1.5.0

16 October 2026. On the demo benchmark a job where nothing changed used to spend 12 seconds in vci before deciding there was nothing to run: a download with the gh CLI, a fetch, a plan, then vci ci planning again from scratch, every project probed one after another and each Rails project booted. Measured now on the same benchmark: vci ci --fetch with nothing changed takes 0.96 s, plus the binary download.

  • The action plans once: for command: ci it runs a single vci ci --fetch, which prints the plan for the step summary and runs what is left; the counts come from the audit log.
  • --fetch [REMOTE] on vci ci and vci plan fetches attestations while the projects are probed, and the fetch itself is one git round trip instead of two. A failed fetch is still a warning and fails open.
  • Projects are probed concurrently: test listing, toolchain and externals per project on their own threads, verdicts too. Output order is unchanged.
  • The Rails toolchain is read without booting the application: one short Ruby process with the bundle set up reports Ruby, Bundler's resolved gems, the test frameworks, the libraries and config/database.yml, in the same format as before, so existing attestations still verify. The plan boots the app only when a candidate attestation records a native library, once per project. The attested run still boots and checks everything. What the plan no longer detects: an app that cannot boot on the verifier for a reason outside its recorded inputs and toolchain; the attested run already booted it, and full runs on no_skip_refs still do.
  • pytest test files are listed without starting Python, following pytest's own rules for the config file, testpaths, python_files, norecursedirs, virtualenvs and the collection options in addopts; an end-to-end test proves the list equals pytest --collect-only. Files that collect_ignore or a plugin would exclude are listed and run on their own, and a file that collects no tests counts as passing, as in a whole-suite run.
  • Lighter go list and cargo metadata --no-deps --offline on the plan side; the action downloads the binary with curl first.
  • VCI_TIMING=1 prints per-phase timings of every plan on stderr; the benchmark workflow uses it.

Upgrade notes. Nothing changes in what is recorded, so existing attestations verify under 1.5.0. Pin @v1 or @v1.5.0.

1.4.1

15 October 2026.

The action never compiles vci in your CI

The GitHub Action downloads the release binary recorded in its release/manifest.txt, verifies its checksum and puts it on the path, in about a second. That was already what @v1 did; what changes is the fallback. A commit of the action with no published binary used to compile vci from source, about two minutes on ubuntu-latest. It now stops in its first step with an error that says which release to use instead. Compiling is opt-in with build-from-source: true (prebuilt: false is a deprecated alias) and, when asked for, uses a cargo cache. Jobs without the gh CLI download with curl or wget; the checksum check is the same.

Version tags now carry their own binaries

Every version tag before this one, v1.0.0 to v1.4.0, points at the commit the binaries were built from, whose manifest still names the previous release, so @v1.4.0 would compile while @v1 downloads. Use @v1, or @v1.4.1 and later: releases are now built as drafts and published by scripts/publish-release.sh, which creates the version tag on the commit that records the manifest, checks that the commit's sources match the binaries it names, and moves v1 there. The example workflows no longer cargo install vci either; they download the binary v1 records.

Measured

Measured on this repository: a benchmark workflow times every stage of vci on the demo projects as its own step, from the plain suite to attesting every unit to a commit with nothing to run.

1.4.0

15 October 2026. vci stops controlling the Rails test database. It is the test engine's business, as it is when you run bin/rails test or rspec: maintain_test_schema!, fixtures and transactional tests give each test its starting state.

  • The databases config/database.yml configures for the test environment are used as they are. vci no longer redirects SQLite files to fresh temp files or loads the schema itself. The bin/rails db:test:prepare child process Active Record starts when the schema is not current is accepted; a test's own child processes are still refused.
  • What the database holds is never an input. Reads, checks and writes of the test environment's SQLite files and their -wal, -shm and -journal files are not recorded, and a listing of db/ leaves them out, so rows written behind the tests' back, or a fresh checkout without any database, change no verdict. Another file an entry of config/database.yml names that is not a SQLite database is still recorded like any file.
  • The schema file of every test database (db/schema.rb, db/cache_schema.rb, ...) is an input of every test that loads Active Record, even on a fresh database where only the db:test:prepare child reads it.
  • MySQL, Trilogy and PostgreSQL test databases work with no policy. The toolchain's database is the adapter name only (sqlite3, mysql2, postgresql), compared exactly; no server version.
  • Still refused: another SQLite file (including a name that merely contains mode=memory), ATTACH, SQLite extensions, a database client a test opens itself, and Active Record connecting to a server or database that is not one of the test environment's (establish_connection elsewhere, an adapter's new_client).
  • Rails files of a project run one at a time in vci run, and vci ci runs the rest in one bin/rails test or rspec process per project.

What you give up. An attestation no longer promises that the test was independent of leftover database state. It promises what CI promises: the test passed on a database the engine set up.

Upgrade notes. policy.rails_allow_db is removed. A vci.toml that still sets it parses, the key has no effect, and vci run and vci plan warn once; remove it. The Ruby collector is now 0.5.0, so existing Rails and RSpec attestations run once more in CI.

1.3.0

15 October 2026. Two things people asked for after the first deployments: CI should not re-run on commit B what it already ran on commit A, and an attestation made on a Mac should count on a Linux runner.

CI attests its own runs

vci ci can now sign what it runs. With --key, the units the plan says to run go through the same path as vci run: inputs recorded, attestation signed and stored. --push publishes them, --ttl sets their lifetime and --remote the destination. On a ref where policy runs everything, such as main, every unit is attested, so the next commit skips each unit whose inputs did not change. A commit that only touches the docs plans everything as SKIP and vci ci finishes without starting a test runner.

The new policy key no_skip_refs_except = ["github-actions"] names the allowed_signers principals whose attestations may still skip on a no_skip_refs ref. Any other signer is refused there by name, so a laptop attestation never skips on main; only the CI key does. Off those refs a key listed there attests nothing, so a pull request run cannot sign with the main key even if a workflow passes it.

The GitHub Action gains signing-key, ttl and push inputs and an attested output. The key must come from a GitHub Environment restricted to the default branch, never a repository secret: every process of the job can read it, and a same-repository pull request runs its own copy of the workflow. The job needs permissions: contents: write to push. Attesting in CI has the setup and the two-job workflow.

The audit log gains attested, pushed, notAttested and attestErrors. A project that cannot run with the collectors runs alone without attesting; the others are still attested, nothing runs twice, and the exit code covers every test.

Proven on this repository's own main branch: the first push attested 13 units, the next push, which changed one pytest module, ran only that test, and a docs-only push ran nothing for pytest, Go and Rust.

Attest on macOS, skip on Linux

policy.libraries = "any" (default "exact"; per project, or per glob in [[policy.platform_overrides]]) makes an attestation made on one platform count on another when the libraries differ only by build. Native libraries opened through FFI, such as Active Storage's libvips, match by library name instead of file name and hash: libvips.42.dylib on a Mac matches libvips.so.42 on Ubuntu, provided libvips is loaded on both sides. The SQLite, libyaml and time-zone data versions of the Rails toolchain, and SQLite and OpenSSL of the pytest toolchain, are not compared. Whether each is loaded still is, so a Python built without _sqlite3 never satisfies an attestation that used it. Ruby and Python versions, the bundle, the environment and every input are compared exactly as before. vci explain prints the policy and each difference it accepted. Nothing changes on the attestation side, so existing attestations verify under the new policy.

Fixed

  • A bundle installed inside the repository, as ruby/setup-ruby's bundler-cache: true does at vendor/bundle, refused every Rails and RSpec file with ruby:read-outside-bundle. Bundler's install directory is now a gem root like any other: nothing under it is a repository input, its gems are externals by version, and RubyGems' and Bundler's own bookkeeping there is not recorded. Still refused, now for bundles anywhere: loading, reading, listing or evaluating anything under a gem root that is not a gem of the bundle, including through Gem.read_binary, Bundler.read_file, Gem::Util.glob_files_in_dir and Gem::Specification.load, and a test's own check of vendor/bundle or of a gem's real path. Require shadowing probes skip gem directories, which makes a Rails file about a third faster to attest.
  • Under libraries = "exact", a native library loaded under another file name is reported as such, with a note that "any" would match it by name.

Upgrade notes. The Ruby collector is now 0.4.2, so existing Rails and RSpec attestations run once more in CI. The @v1 action before this version ignores the signing-key input and rejects no_skip_refs_except and libraries in a base policy, so everything runs; move to 1.3.0 before adding either key.

1.2.0

14 October 2026. Everything in this release came out of setting vci up in a large Rails + Rust + Go + TypeScript monorepo and measuring what refused to attest.

Rails apps with Active Storage can attest

Rails 8.1 loads ruby-vips at boot through Active Storage, and its FFI load tainted every test file, so a whole app attested nothing. Now a native library load is recorded as a hashed external (native:libvips) instead of a refusal; only calls into attached functions refuse. ruby-vips gets Ruby-level hooks: image loaders, savers and thumbnails record the image file as an input, while unknown vips operations, descriptors, text rendering and file-typed options still refuse. In the new fixture a model test attests, a test that attaches and analyses an image attests with the PNG as an input (editing the PNG re-runs only that test), and an arbitrary FFI call is refused.

Also fixed

  • Collector files reached through a symlinked install prefix (Homebrew's opt/) were recorded as inputs outside the repository, which blocked every node-test file on Homebrew installs.
  • Minitest files that never load Rails were refused with a spurious toolchain mismatch (rails "").
  • A failed ffi_lib load no longer taints.
  • OpenSSL certificate files and SSL_CERT_FILE / SSL_CERT_DIR, read in C, are now inputs.
  • Found by the adversarial pass over the new rules and closed before release: paths starting with ~ or |, case-insensitive vips operation names, directory symlinks into exempt locations, Method#super_method around FFI wrappers, and uid/identity reads.

New

  • policy.allow_superuser_mismatch (default off) lets CI runners that run as root accept attestations made as a normal user. vci explain names the key when the check fails. Read the warning in the configuration page before turning it on.
  • vci run groups refusals by a stable reason with full counts instead of capping at twelve groups, and vci run --summary FILE writes a JSON summary of every unit and its reasons for scripted coverage measurement.
  • vci init in a linked git worktree says that the metadata remote went into the shared .git/config.

Upgrade note. The Ruby collector is now 0.4.1, so existing Rails attestations run once more in CI.

1.1.0

14 October 2026.

New adapter: node-test

For projects that run Node's built-in test runner (node --test). It parses the package.json test script, including leading env assignments, --import hooks, --experimental-strip-types, quoted globs and ${VAR:+…} expansions, and supports pnpm workspaces. Each file runs in its own process with a collector preloaded ahead of the user's hooks; a reporter counts results so skipped, todo, only-filtered, load-error and early-exit files are never attested. Works on Node 22, 24 and 26.

From adversarial testing of the new adapter

  • pretest and posttest scripts and .npmrc node-options are inputs or refusals.
  • NODE_OPTIONS set in an --env-file follows the environment policy.
  • The node --test orchestrator process is observed, not only the per-file children.
  • pnpm file: dependencies are hashed by content, not identified by version.
  • The host time zone is an input when TZ is unset.
