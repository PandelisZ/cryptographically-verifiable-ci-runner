GitHub Actions

The repository ships a composite action. It installs vci, fetches attestations, prints the plan, and runs only the tests no valid attestation covers.

Before you start

  1. vci.toml and .vci/allowed_signers are merged to your default branch (setup guide).
  2. .git-meta is committed, and attestations are pushed with vci push before or together with the branch.

Workflow

Save as .github/workflows/test.yml. Set up your language toolchain first, then call the action. Replace <commit-sha> with a full commit SHA of the vci repository.

name: test

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # the base commit must be available

      - uses: actions/setup-node@v4
        with:
          node-version: 22          # same Node major version as used locally
          cache: npm

      - run: npm ci

      - uses: PandelisZ/cryptographically-verifiable-ci-runner@<commit-sha>

For several languages in one job, set up every toolchain and call the action once.

Run on the hosted runner directly, not in a container: job. Attestations made as a normal user are not accepted by a verifier running as root.

What the action does

  1. Downloads a prebuilt vci binary whose checksum is recorded in the pinned action, or builds from source and caches the result.
  2. Runs vci fetch --remote origin to fetch refs/meta/main. A read-only contents: read token is enough. If the fetch fails, it warns and everything runs.
  3. Runs vci plan and writes the plan to the job summary.
  4. Runs vci ci, which runs what was not skipped and writes an audit log.

Security rules

  • Pin the action to a commit SHA. The action is the verifier. A branch or tag reference can move.
  • Never build vci from the pull request's own checkout. A pull request could change the verifier that checks it.
  • Leave base-ref at its default unless you know the ref is outside the pull request's control.
  • Keep refs/heads/main in policy.no_skip_refs, so pushes to the default branch run everything.
  • Use pull_request, not pull_request_target. Pull requests from forks cannot push attestations to your repository, so they get no skips and every test runs.
  • Revoke by removing the line from .vci/allowed_signers on the default branch.
  • Always pass --remote to vci fetch when not using the action, so the checkout never chooses where attestations come from.

Who can push attestations

vci push writes refs/meta/main. Anyone with push access to the repository can write, overwrite or delete metadata there. That is safe by design: an attestation only counts when its signature verifies against a key in the base commit's .vci/allowed_signers and it matches the unit, repository, toolchain and inputs exactly. A deleted or overwritten attestation only makes its unit run.

A repository ruleset on refs/meta/** can further restrict who may write.

Prebuilt binaries

The action downloads a release binary instead of compiling, which takes a few seconds instead of about two minutes. It does so only when:

  • release/manifest.txt in the pinned action names a release built from exactly the action's own sources;
  • a binary exists for the runner (Linux and macOS, x86_64 and arm64);
  • the download's SHA-256 equals the checksum in release/manifest.txt.

Otherwise it builds from source. The checksums are part of the pinned action, so replacing a release asset cannot change what runs.

Troubleshooting

SymptomLikely cause
Everything runs on a pull requestvci.toml or .vci/allowed_signers is not on the base branch yet, or attestations were not pushed (git ls-remote origin refs/meta/main is empty)
failed check: toolchainPython, Node, uv, Ruby, Bundler or package versions differ between the laptop and the runner
failed check: inputsA file the test depends on changed after it was attested; vci explain names it
failed check: signerThe signing key is not in the base commit's allowed_signers, or it has expired
A Go package or cargo target never skips on the runnerIts code depends on the platform (build tags, cfg(target_os), runtime.GOOS, floating-point maths): such units are only accepted on the same OS and architecture
A test reads CI, HOME or TMPDIRThose values differ on a runner, so that file always runs there
No Rails test file ever skips on the runnerSee getting skips on a Linux runner

Run vci explain <file> --base-ref origin/main locally for the full reason.
