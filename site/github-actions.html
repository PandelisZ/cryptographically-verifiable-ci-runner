GitHub Actions

Add one step to your workflow. It skips every test that a trusted person or agent already ran against the same code, and runs the rest.

The one line

Put this after your checkout and toolchain setup steps:

- uses: PandelisZ/cryptographically-verifiable-ci-runner@v1

A few terms used on this page:

  • Unit: the smallest thing vci can skip. A test file for Vitest, pytest, Minitest and RSpec; a package for Go; a test target for Rust.
  • Attestation: a record, signed with an SSH key, that says "this unit passed against exactly these inputs".
  • Base branch: the branch a pull request merges into, usually main. CI reads the trusted keys and the policy from its commit, never from the pull request.

@v1 follows the latest tested 1.x release. See pinning for stricter options.

Before you start

  1. vci.toml and .vci/allowed_signers are merged to your default branch (setup guide).
  2. .git-meta (written by vci init) is committed.
  3. Attestations are pushed with vci push before, or together with, the branch.

A complete workflow

Save this as .github/workflows/test.yml. It is for Vitest; for other runners, swap the toolchain steps for the ones below.

name: test

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read            # read-only is enough

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0    # the base commit must be available

      # Your toolchain, at the same version as locally
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci

      - uses: PandelisZ/cryptographically-verifiable-ci-runner@v1

Run on the hosted runner directly, not in a container: job. Attestations made as a normal user are not accepted by a verifier running as root.

What the action does

  1. Installs vci: a prebuilt binary whose checksum is recorded in the pinned action, or a build from source (cached).
  2. Runs vci fetch --remote origin. This fetches refs/meta/main, the git ref where attestations live. A contents: read token is enough. If the fetch fails, it warns and every test runs.
  3. Runs vci plan and writes the plan to the job summary.
  4. Runs vci ci: it runs every unit that was not skipped and writes an audit log. The job fails if any test fails.

Pinning

The action is the verifier, so choose how far it may move:

ReferenceMoves?Use when
@v1only to tested 1.x releasesthe default
@v1.0.0neveryou want a specific release
@<full commit SHA>neverstrictest pinning; the SHA is on each release page

Never reference a branch.

Prebuilt binaries

By default the action downloads a release binary, which takes a few seconds instead of about two minutes of compiling. It uses the download only when the pinned action's release/manifest.txt names a release built from exactly the action's own sources, a binary exists for the runner (Linux or macOS, x86_64 or arm64), and its SHA-256 equals the checksum in that manifest. Otherwise it builds from source and caches the result; because the checksums are part of the pinned action, replacing a release asset cannot change what runs.

Security rules

CI takes its rules from the base branch and only looks at code and attestations from the pull request:

  • Pin the action. It is the verifier (see pinning).
  • Never build vci from the pull request's own checkout. The pull request could change the verifier that checks it.
  • Leave base-ref at its default, unless you know the ref is outside the pull request's control.
  • Keep refs/heads/main in policy.no_skip_refs. Pushes to the default branch then run everything.
  • Use pull_request, not pull_request_target. Fork pull requests cannot push attestations, so every test runs for them.
  • Revoke a signer by removing their line from .vci/allowed_signers on the default branch.
  • Without the action, always pass --remote to vci fetch, so the checkout never chooses where attestations come from.

Who can push attestations

vci push writes refs/meta/main. Anyone with push access to the repository can write, overwrite or delete metadata there.

That is safe by design. An attestation only counts when its signature verifies against a key in the base commit's .vci/allowed_signers, and it matches the unit, repository, toolchain and inputs exactly. A deleted or overwritten attestation only makes its unit run.

Anyone who can push metadata can also turn on git-meta's auto-prune or filter rules for everyone. Pruned attestations only make their units run, and vci fetch warns about such settings in the action's log.

To limit who may write, add a repository ruleset on refs/meta/**.

Without the action

      - name: Install vci
        run: |
          git clone \
            https://github.com/PandelisZ/cryptographically-verifiable-ci-runner \
            "$RUNNER_TEMP/vci"
          git -C "$RUNNER_TEMP/vci" checkout v1.0.0
          cargo install --locked --path "$RUNNER_TEMP/vci/crates/vci-cli"
          echo "VCI_PY_PLUGIN=$RUNNER_TEMP/vci/py/pytest-plugin" >> "$GITHUB_ENV"
          echo "VCI_JS_PLUGIN=$RUNNER_TEMP/vci/js/vitest-plugin" >> "$GITHUB_ENV"
          echo "VCI_RUBY_COLLECTOR=$RUNNER_TEMP/vci/ruby/vci-collector" >> "$GITHUB_ENV"

      - run: vci fetch --remote origin

      - run: |
          vci ci \
            --base-ref "${{ github.event.pull_request.base.sha || github.sha }}" \
            --audit-log vci-audit.json

Troubleshooting

Run vci explain <file> --base-ref origin/main locally for the full reason a unit ran.

SymptomLikely cause
Everything runs on a pull requestvci.toml or .vci/allowed_signers is not on the base branch yet, or attestations were not pushed (git ls-remote origin refs/meta/main is empty)
failed check: toolchainPython, Node, uv, Ruby, Bundler or package versions differ between the laptop and the runner
failed check: inputsA file the test depends on changed after it was attested; vci explain names it
failed check: signerThe signing key is not in the base commit's allowed_signers, or it has expired
A Go package or cargo target never skips on the runnerIts code depends on the platform (build tags, _linux.go files, cfg(target_os), runtime.GOOS, floating-point maths); such units are only accepted on the same OS and architecture
A test reads CI, HOME or USERThose values differ on a runner, so that file always runs there
No Rails test file ever skips on the runnerSee Rails: laptop to Linux runner
An RSpec file is never attestedAn example was pending, skipped, filtered out or retried, or the process exited non-zero after the report; vci run prints the reason (rspec:filtered:..., rspec:retry, ...)
Minitest files never run with runner = "rspec"An explicit runner leaves the other runner's files to you; vci plan and vci ci warn, and the audit log lists it under warnings
