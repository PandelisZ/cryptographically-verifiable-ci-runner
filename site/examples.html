A full round trip

An agent on a laptop (macOS arm64) changes a Rails model, runs the spec that covers it, and opens a pull request. CI (Ubuntu x86_64) skips what the agent already ran. This is pull request 4 of this repository.

1. Run and sign locally

TZ=UTC vci run spec/models/b_spec.rb spec/lib/a_spec.rb --key ~/.ssh/id_ed25519
3 examples, 0 failures

vci: attested demo/rspec-app/spec/lib/a_spec.rb (65 inputs, root 2cbdcb32a9721b03)
     as git-meta path:demo/rspec-app/spec/lib/a_spec.rb vci:attestation:…
vci: attested demo/rspec-app/spec/models/b_spec.rb (7517 inputs, root 9b40ad198ee598ce)
     as git-meta path:demo/rspec-app/spec/models/b_spec.rb vci:attestation:…
vci: 2 attested, 0 not attested

The input counts differ for a reason. a_spec.rb only loads spec_helper.rb and one library file. b_spec.rb boots Rails, so its inputs include every file Rails loaded or looked for.

2. See what CI will do

TZ=UTC vci plan --base-ref origin/main
SKIP demo/rspec-app/spec/lib/a_spec.rb [rspec]      (attested by vci-demo-agent (SHA256:RASHZ3Nm…))
SKIP demo/rspec-app/spec/models/b_spec.rb [rspec]   (attested by vci-demo-agent (SHA256:RASHZ3Nm…))
RUN  demo/rspec-app/spec/requests/d_spec.rb [rspec] (no attestation)
RUN  demo/rspec-app/spec/views/c_spec.rb [rspec]    (no attestation)

3. Push the attestations and the branch

vci push        # git-meta metadata on refs/meta/main
git push        # your branch, as usual

4. CI skips what was attested

From the Actions log of that pull request, which also covers the repository's Python, Go, Rust and Minitest demo projects:

using vci v0.3.0 (vci-x86_64-unknown-linux-musl.tar.gz, sha256 fdf03d19…)
vci: fetched git-meta metadata from meta (9 attestations stored locally)
SKIP demo/go-app/b [go]                              (attested …)
SKIP demo/rails-app/test/models/b_test.rb [rails]    (attested …)
SKIP demo/rspec-app/spec/lib/a_spec.rb [rspec]      (attested …)
SKIP demo/rspec-app/spec/models/b_spec.rb [rspec]   (attested …)
RUN  demo/rspec-app/spec/requests/d_spec.rb [rspec] (no attestation)
RUN  demo/rspec-app/spec/views/c_spec.rb [rspec]    (no attestation)

4 to skip, 17 to run

5. A later change invalidates only what it touches

A second commit edits a FactoryBot factory and does not re-run anything locally. CI runs the spec that uses the factory again, and still skips the one that does not load it:

SKIP demo/rspec-app/spec/lib/a_spec.rb [rspec]     (attested …)
RUN  demo/rspec-app/spec/models/b_spec.rb [rspec]  (no valid attestation (1 candidates;
     best failed inputs: entry:demo/rspec-app/spec/factories/gadgets.rb))

vci explain spec/models/b_spec.rb --base-ref origin/main

candidate 1: git-meta path:demo/rspec-app/spec/models/b_spec.rb vci:attestation:475cf8ee…

  issued 2026-10-03T05:32:00Z, expires 2026-10-17T05:32:00Z
  failed check: inputs
    (expected: recorded in the attestation; actual: this checkout / CI now)
    entry:demo/rspec-app/spec/factories/gadgets.rb

      actual:   file exec=false size=80 blake3=e756de105a350d6a…

Each candidate attestation is listed with the first check it failed. The common ones:

Failed checkMeaningWhat to do
inputsA file, directory listing or env var the test used has changedRun the test again with vci run
toolchainLanguage, runner or library versions differ between the two machinesPin the same versions on both sides; see Test runners
signerThe key is not in .vci/allowed_signers on the base branch, or has expiredAdd the key on the default branch
expiryThe attestation is older than its lifetime or max_ttlRun the test again

Setup for each runner

Each example is a complete starting point: the config, the local commands, and the CI steps. Run the local commands in the project directory.

vci.toml

project = "."
adapter = "vitest"

[policy]
platform = "any"
no_skip_refs = ["refs/heads/main", "refs/tags/**"]

[env]
mode = "strict"
global = ["NODE_ENV"]

Locally

vci run src/cart.test.ts src/price.test.ts --key ~/.ssh/id_ed25519
vci plan --base-ref origin/main
vci push

- uses: actions/checkout@v4

    fetch-depth: 0

When vci refuses to attest

Some tests cannot be vouched for, and vci run says so instead of signing. Two spec files as an example:

# spec/lib/shell_spec.rb
it "asks git for its version" do
  expect(`git --version`).to include("git")
end

# spec/lib/pending_spec.rb
it "adds" do
  expect(1 + 1).to eq(2)
end

xit "subtracts"
vci: not attesting demo/rspec-app/spec/lib/pending_spec.rb: result failed (0 failed, 1 skipped or
     xfailed of 2; a skipped test did not run, so it cannot be vouched for elsewhere)
vci: not attesting demo/rspec-app/spec/lib/shell_spec.rb: tainted: process:backtick
vci: 0 attested, 2 not attested

Both files passed. They are refused because:

  • the first starts a child process, and what that process reads is invisible to the collector;
  • the second has an example that did not run, so nobody has checked it.

A refused test is not an error. It runs in CI as it always did.

You seeCause
tainted: process:…The test started a child process
tainted: network:… or socket…The test opened a network connection
result failed (… skipped …)A test or example was skipped or pending
rspec:filteredA focus or tag filter left examples out of the run
wrote inside the repository: <path>The test changed a tracked location
input outside the repository: <path>The test read a file CI will not have
env:enumeratedThe test read the whole environment, not named variables

Tests you know depend on something vci cannot see belong under never_skip in vci.toml.

Several runners in one repository

This repository's own vci.toml holds five projects with four adapters:

[policy]
platform = "any"
max_ttl = "30d"
no_skip_refs = ["refs/heads/main", "refs/tags/**"]

[env]
mode = "strict"
global = ["TZ", "CGO_ENABLED"]

[[projects]]
name = "py"
path = "demo/pytest-app"
adapter = "pytest"

[[projects]]
name = "go"
path = "demo/go-app"
adapter = "go"

[[projects]]
name = "rust"
path = "demo/cargo-app"
adapter = "cargo"

[[projects]]
name = "rails"
path = "demo/rails-app"
adapter = "rails"

[[projects]]
name = "rspec"
path = "demo/rspec-app"
adapter = "rails"
runner = "rspec"

From the repository root, one command takes units of any project. vci finds the project each belongs to:

vci run demo/rspec-app/spec/models/b_spec.rb demo/go-app/b 'demo/cargo-app/a#lib' --key ~/.ssh/id_ed25519

In CI, set up every toolchain and call the action once. The workflow:

env:
  UV_PYTHON_PREFERENCE: only-managed
  CGO_ENABLED: "0"
  TZ: UTC
steps:
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0
  - uses: astral-sh/setup-uv@v6
    with: { version: "0.11.7" }
  - uses: actions/setup-go@v5
    with: { go-version: "1.26.2" }
  - uses: dtolnay/rust-toolchain@master
    with: { toolchain: "1.95.0" }
  - uses: ruby/setup-ruby@v1
    with: { ruby-version: "3.4.9", bundler-cache: true, working-directory: demo/rails-app }
  - uses: ruby/setup-ruby@v1
    with: { ruby-version: "3.4.9", bundler-cache: true, working-directory: demo/rspec-app }
  - run: |
      (cd demo/pytest-app && uv sync --locked)
      (cd demo/go-app && go mod download)
      (cd demo/cargo-app && cargo fetch --locked)
  - uses: ./        # in your repository: PandelisZ/cryptographically-verifiable-ci-runner@<commit-sha>

The whole job, with 21 units across five projects, takes under a minute. The vci step itself takes about ten seconds.

Looking at attestations in git

Attestations are git-meta metadata. There is no server and no separate database: they live on refs/meta/main of your repository and travel with git push and git fetch.

git ls-remote origin 'refs/meta/*'
d413f4b9835da1961068518613a00524f0034690	refs/meta/main

Each attestation is attached to the path of the unit it covers. With the git meta CLI installed (cargo install git-meta-cli) you can read them directly:

git meta get path:demo/go-app/b
demo/go-app/b;vci:attestation:a2ad9aa8…:4404876773660987:61dfaf94…  {"payloadType":"application/vnd.in-toto+json", …}
demo/go-app/b;vci:attestation:a2ad9aa8…:4404876773660987:74cca9cb…  {"payloadType":"application/vnd.in-toto+json", …}

The key has three parts after vci:attestation: a hash of the unit's id, the signer's id, and a hash of everything the attestation covers. The value is the signed envelope. Two entries here mean the same signer attested the package against two different sets of inputs.

Metadata is not trusted on its own. Anyone who can push to the repository can write or delete these values. A value only leads to a skip when its signature verifies against a key in the base branch's .vci/allowed_signers, and every input still matches. Deleting one only makes that test run.

To drop expired attestations:

vci prune --dry-run
vci prune && vci push

An agent's loop

An agent uses the same commands as a person. Give it its own key, listed in .vci/allowed_signers on the default branch with an expiry:

build-agent namespaces="vci-attest",valid-before="20270101" ssh-ed25519 AAAAC3Nza…

Then, after each change it makes:

export VCI_SIGNING_KEY=~/.config/vci/agent_ed25519   # so --key can be left out

vci run spec/models/order_spec.rb     # the tests that cover the change
vci plan --base-ref origin/main       # optional: confirm what CI will skip
vci push && git push

Several agents can work on one branch. Each signs with its own key, their attestations never overwrite each other, and CI accepts any of them that is still valid.
