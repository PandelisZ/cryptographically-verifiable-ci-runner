CLI reference

You use three commands every day (run, plan, push). One runs in CI (ci). One answers "why did this test run?" (explain).

Commands

A unit is what vci can skip: a test file, a Go package or a Cargo test target. An attestation is a signed record that a unit passed against exactly these inputs.

CommandPurpose
vci initSet up a repository: config, trusted signers, metadata remote
vci runRun tests locally and sign an attestation for each unit that passed
vci planShow which units can be skipped and why the others run
vci pushPublish your attestations to the remote
vci fetchDownload attestations from the remote
vci ciIn CI: plan, run the rest, write an audit log; with a key, attest what ran
vci explainShow why one unit was not skipped
vci pruneDelete expired attestations
vci verifyVerify one attestation envelope and print its claims

vci init

vci init [--adapter vitest|pytest|go|cargo|rails]
         [--key K] [--principal P] [--project DIR]
         [--no-install] [--meta-url URL]

Writes vci.toml, .vci/allowed_signers (adding key K) and .git-meta, configures the git-meta remote, and prints a CI snippet.

  • --adapter: the test runner. Default vitest.
  • --key: a public key, or a private key with its .pub next to it. --principal names its owner (default: git config user.email).
  • --project DIR: the project directory, relative to the repository root.
  • --no-install: for Vitest, skip the npm install of @vci/vitest.
  • --meta-url: where attestations are exchanged (default: origin's URL). Without an origin remote or this flag, no .git-meta is written.
vci init --adapter pytest --key ~/.ssh/id_ed25519.pub

vci run

vci run [UNITS…] [--key PATH] [--ttl 14d]

Runs tests with input collection on, then signs and stores an attestation for every unit that can be attested. With no arguments it runs every unit. The exit code is the test runner's.

  • Units are test files, Go package directories (./b), or Cargo targets (crates/b#test:name; a package directory means all its targets).
  • --key: the SSH signing key (see signing key).
  • --ttl: how long the attestation is valid. Default 14d.
TZ=UTC vci run spec/models/b_spec.rb spec/lib/a_spec.rb --key ~/.ssh/id_ed25519
3 examples, 0 failures

vci: attested demo/rspec-app/spec/lib/a_spec.rb (65 inputs, root 2cbdcb32a9721b03)
     as git-meta path:demo/rspec-app/spec/lib/a_spec.rb vci:attestation:…
vci: attested demo/rspec-app/spec/models/b_spec.rb (7517 inputs, root 9b40ad198ee598ce)
     as git-meta path:demo/rspec-app/spec/models/b_spec.rb vci:attestation:…
vci: 2 attested, 0 not attested

vci plan

vci plan [--base-ref R] [--format text|json|github]

Prints which units can be skipped and why the others run. Changes nothing.

  • --base-ref: the commit trust is read from (see base ref).
  • --format: text (default), json or github.
vci plan --base-ref origin/main
SKIP tests/test_b.py  (attested by alice@example.com (SHA256:tsNeKgQt…))
RUN  tests/test_a.py  (no attestation)
1 to skip, 1 to run

vci push, vci fetch

vci push [--remote R]
vci fetch [--remote R]

Exchange attestations on refs/meta/main, like git meta push and git meta pull. Push your branch with git push as usual.

  • --remote R: a git-meta remote, or a git remote or URL to use as one. Default: the configured git-meta remote, else the url: in .git-meta, else origin.
  • In CI, always pass --remote, so the checkout never chooses where attestations come from.
vci push && git push              # on your laptop
vci fetch --remote origin         # in CI (the action does this)

vci ci

vci ci [--base-ref R] [--audit-log PATH]
       [--key PATH [--ttl 14d] [--push [--remote R]]]

Plans, runs every unit that was not skipped, and exits non-zero if any test fails. The GitHub Action runs it for you. When every unit is skipped, it prints nothing to run and never starts the test runner.

  • --audit-log PATH: write a JSON record of every skip, by whom, and what ran.
  • --key PATH: run what is left the way vci run --key does, and attest every unit that passed. When the plan runs everything (for example on a no_skip_refs ref with an empty no_skip_refs_except), every unit is attested. The next commit's CI then skips each unit whose inputs did not change. See attesting in CI.
  • --ttl: lifetime of those attestations. Default 14d.
  • --push: afterwards, publish them as vci push does, whether or not the tests passed. A failed push prints a warning and does not change the exit code.
  • --remote R: where --push pushes, as for vci push.

With --key, the audit log also lists the attested units and whether they were pushed. A key whose principal is in policy.no_skip_refs_except attests nothing on other refs, such as a pull request's.

vci ci --base-ref origin/main --audit-log vci-audit.json
vci ci --base-ref "$GITHUB_SHA" --key "$RUNNER_TEMP/vci-key" --push --remote origin   # on main

vci explain

vci explain <unit> [--base-ref R]

Lists every candidate attestation for one unit and the first check each failed, with expected and actual values.

vci explain spec/models/b_spec.rb --base-ref origin/main

Full output and what each failed check means: Examples.

vci prune

vci prune [--dry-run]

Deletes expired attestations from the local store. vci push publishes the deletions. --dry-run only lists them.

vci prune --dry-run
vci prune && vci push

vci verify

vci verify <envelope|-> [--allowed-signers F] [--base-ref R]

Verifies one DSSE envelope (a file, or - for stdin) and prints its claims.

  • --allowed-signers F: the trust file to check against. Default: .vci/allowed_signers at --base-ref, or at HEAD.

Signing key

vci signs with an SSH key. It uses the first of:

  1. --key PATH
  2. $VCI_SIGNING_KEY
  3. git config user.signingkey, when gpg.format = ssh

A GPG key is never used. A .pub path works when the private half is in ssh-agent, hardware keys included.

Base ref

The base ref is the commit vci trusts: it reads the policy and the allowed signers from there, never from the code under test. vci uses the first of:

  1. --base-ref R
  2. $VCI_BASE_REF
  3. origin/$GITHUB_BASE_REF
  4. the first that exists of origin/HEAD, origin/main, origin/master, main, master

If none resolves, everything runs. vci plan warns when the base commit is HEAD or contains it, because then trust would come from the commit under test.

Environment variables

VariableMeaning
VCI_SIGNING_KEYSigning key path, when --key is not given
VCI_BASE_REFBase ref, when --base-ref is not given
VCI_JOBSParallel pytest or go test processes in vci run (default: CPUs, up to 8). Rails files run one at a time: they share the test database.
VCI_JS_PLUGINPath of the @vci/vitest package (default: node_modules/@vci/vitest above the project)
VCI_PY_PLUGINThe py/pytest-plugin directory
VCI_RUBY_COLLECTORThe ruby/vci-collector directory
VCI_NODE, VCI_UV, VCI_GO, VCI_CARGO, VCI_RUBYBinary to use for each toolchain, instead of the one on PATH

The three collector paths are not needed with Homebrew or the GitHub Action, which set them up for you.

Looking at attestations directly

Attestations are ordinary git-meta values, so the git meta CLI can read them:

git meta get path:src/b.test.ts
git ls-remote origin refs/meta/main
