CLI reference

You use three commands every day (run, plan, push). One runs in CI (ci). One answers "why did this test run?" (explain).

Commands

A unit is what vci can skip: a test file, a Go package or a Cargo test target. An attestation is a signed record that a unit passed against exactly these inputs.

CommandPurpose
vci initSet up a repository: config, trusted signers, metadata remote
vci runRun tests locally and sign an attestation for each unit that passed
vci planShow which units can be skipped and why the others run
vci pushPublish your attestations to the remote
vci fetchDownload attestations from the remote
vci ciIn CI: plan, run the rest, write an audit log; with a key or the job's OIDC token, attest what ran
vci explainShow why one unit was not skipped
vci envShow which environment variables vci sets, hashes, ignores and removes
vci pruneDelete expired attestations
vci verifyVerify one attestation envelope and print its claims
vci store infoShow which attestation store the repository uses and how it is set up
vci updateInstall the latest release the way vci was installed

vci init

vci init [--adapter vitest|pytest|go|cargo|rails]
         [--key K] [--principal P] [--project DIR]
         [--no-install] [--meta-url URL] [--oidc]

Writes vci.toml, .vci/allowed_signers (adding key K) and .git-meta, configures the git-meta remote, and prints a CI snippet.

  • --adapter: the test runner. Default vitest.
  • --key: a public key, or a private key with its .pub next to it. --principal names its owner (default: git config user.email).
  • --project DIR: the project directory, relative to the repository root.
  • --no-install: for Vitest, skip the npm install of @vci/vitest.
  • --meta-url: where attestations are exchanged (default: origin's URL). Without an origin remote or this flag, no .git-meta is written.
  • --oidc (since 2.0): also trust this repository's GitHub Actions workflow signing keylessly. Writes .vci/identities.toml (pushes to origin's default branch, principal github-actions; an existing file is left alone) and the Sigstore trust root from gh attestation trusted-root.
vci init --adapter pytest --key ~/.ssh/id_ed25519.pub

vci run

vci run [UNITS…] [--key PATH | --oidc[=github|public-good]] [--ttl 14d]

Runs tests with input collection on, then signs and stores an attestation for every unit that can be attested. With no arguments it runs every unit. The exit code is the test runner's.

  • Units are test files, Go package directories (./b), or Cargo targets (crates/b#test:name; a package directory means all its targets).
  • --key: the SSH signing key (see signing key).
  • --oidc (since 2.0): in a GitHub Actions job with permissions: id-token: write, sign keylessly with the job's OIDC token instead (see keyless attestation). The instance needs the =: vci run --oidc a_test.go runs a_test.go.
  • --ttl: how long the attestation is valid. Default 14d.
vci run spec/models/b_spec.rb spec/lib/a_spec.rb --key ~/.ssh/id_ed25519
3 examples, 0 failures

vci: attested demo/rspec-app/spec/lib/a_spec.rb (65 inputs, root 2cbdcb32a9721b03)
     as git-meta path:demo/rspec-app/spec/lib/a_spec.rb vci:attestation:…
vci: attested demo/rspec-app/spec/models/b_spec.rb (7517 inputs, root 9b40ad198ee598ce)
     as git-meta path:demo/rspec-app/spec/models/b_spec.rb vci:attestation:…
vci: 2 attested, 0 not attested

vci plan

vci plan [--base-ref R] [--format text|json|github]

Prints which units can be skipped and why the others run. Changes nothing.

  • --base-ref: the commit trust is read from (see base ref).
  • --format: text (default), json or github.
vci plan --base-ref origin/main
SKIP tests/test_b.py  (attested by alice@example.com (SHA256:tsNeKgQt…))
RUN  tests/test_a.py  (no attestation)
1 to skip, 1 to run

vci push, vci fetch

vci push [--remote R]
vci fetch [--remote R]

Exchange attestations on refs/meta/main, like git meta push and git meta pull. Push your branch with git push as usual. Since 2.0 a fetch downloads the keys, not the values; plan, explain, verify, run and prune fetch the values they read, and a value that cannot be fetched (offline) makes its unit run.

  • --remote R: a git-meta remote, or a git remote or URL to use as one. Default: the configured git-meta remote, else the url: in .git-meta, else origin.
  • In CI, always pass --remote on git-meta, so the checkout never chooses where attestations come from. On any other store there is nothing to exchange, and --remote exits 2 (what fetch and push mean).
vci push && git push              # on your laptop
vci fetch --remote origin         # in CI (the action does this)

vci ci

vci ci [--base-ref R] [--audit-log PATH] [--fetch [R]] [--project NAME]... [--partition I/N]
       [--key PATH | --oidc[=INSTANCE]] [--ttl 14d] [--push [--remote R]]

Plans, runs every unit that was not skipped, and exits non-zero if any test fails. The GitHub Action runs it for you. When every unit is skipped, it prints nothing to run and never starts the test runner.

  • --audit-log PATH: write a JSON record of every skip, by whom, and what ran.
  • --key PATH: run what is left the way vci run --key does, and attest every unit that passed. When the plan runs everything (for example on a no_skip_refs ref with an empty no_skip_refs_except), every unit is attested. The next commit's CI then skips each unit whose inputs did not change. See attesting in CI.
  • --oidc (since 2.0): the same, keylessly, with the GitHub Actions job's OIDC token (permissions: id-token: write, no secret). The job's identity must match an entry of .vci/identities.toml on the base branch.
  • --partition I/N (since 2.0): run only partition I of N shares of what the plan runs, for a matrix of N jobs. A unit belongs to the partition its test id hashes to, the same in every job and on every machine, so every unit runs in exactly one job; what the plan skips is skipped in all of them. A project a job cannot list runs whole in that job, with a warning. With --key --push each job attests and publishes its share. See splitting a suite over jobs.
  • --ttl: lifetime of those attestations. Default 14d.
  • --push: afterwards, publish them as vci push does, whether or not the tests passed. A failed push prints a warning and does not change the exit code.
  • --remote R: where --push pushes, as for vci push.

With --key or --oidc, the audit log also lists the attested units and whether they were pushed. A key or identity whose principal is in policy.no_skip_refs_except attests nothing on other refs, such as a pull request's.

vci ci --base-ref origin/main --audit-log vci-audit.json
vci ci --base-ref "$GITHUB_SHA" --key "$RUNNER_TEMP/vci-key" --push --remote origin   # on main

vci explain

vci explain <unit> [--base-ref R]

Lists every candidate attestation for one unit and the first check each failed, with expected and actual values.

vci explain spec/models/b_spec.rb --base-ref origin/main

Full output and what each failed check means: Examples. An environment failure names the variable and its class under the base policy, never its value:

  failed check: env
    env:FEATURE_SEARCH (hash)
      expected: blake3=5d2a6bf0...
      actual:   unset

vci env

vci env [--base-ref R] [--project NAME] [--format text|json]

Prints the effective environment policy of each project, as vci applies it on this machine. It runs nothing.

  • One row per variable the lists name: its class (set, hash, ignore, built-in hash, built-in ignore, or stripped), where the rule comes from (vci.toml set, vci.toml hash, vci.toml global (old name of hash), built-in go, test script, ...) and what it is here (the value vci sets, present (<hash prefix>), present or absent).
  • Built-in variables not set here, and variables present here that the tests will not see, are listed below the table.
  • --base-ref R: adds a BASE column with what the base commit's policy (the one CI judges with) does differently, = where it agrees.
  • --project NAME: one project only. --format json: every row, for scripts.
vci env --base-ref origin/main

vci prune

vci prune [--dry-run]

Deletes expired attestations from the attestation store: with git-meta from the local store, and vci push publishes the deletions; SQLite, PostgreSQL and libSQL delete at once. --dry-run only lists them. It reads every attestation, so since 2.0 it first fetches the ones a fetch left out.

vci prune --dry-run
vci prune && vci push

vci verify

vci verify <envelope|-> [--allowed-signers F] [--identities F --trusted-root F] [--base-ref R]

Verifies one DSSE envelope (a file, or - for stdin) and prints its claims.

  • --allowed-signers F: the trust file for an SSH-signed envelope. Default: .vci/allowed_signers at --base-ref, or at HEAD.
  • --identities F, --trusted-root F: the trust for a keyless (--oidc) envelope. Default: .vci/identities.toml and .vci/sigstore-trusted-root.json at --base-ref, or at HEAD.
  • Trust given on the command line is the only trust: once any of these is given, an envelope whose kind needs a file that was not given is INVALID.

vci store info

vci store info [--format text|json]

Since 2.8.0. Says which attestation store the repository uses (git-meta, SQLite, PostgreSQL or libSQL) and how it was chosen: its location, every setting with where it came from ($VCI_STORE, $VCI_STORE_URL, vci.toml, the default), what it can do, whether it exists and how many attestations it holds. It never prints a password or a token: a token that [store] token_command prints shows as token: (from token_command: <the command>). In a linked worktree, git-meta's location is the common git directory's store, which every worktree of the repository shares.

  • Exit 0 when the store can be read, also before anything is stored; otherwise it prints what it knows, then the error, and exits 2. Run it first when a plan says it cannot read the store.
  • --format json: the same, for scripts.
VCI_STORE=sqlite vci store info

vci update

vci update [--check] [--version X.Y.Z] [--keep-old]

Since 2.7.33. Finds the latest release (where GitHub's releases/latest redirects; no token) and, when it is newer than this vci, installs it the way this one was installed. vci upgrade is the same command.

  • Homebrew (the binary is under Cellar/vci/): runs brew update and brew upgrade pandelisz/tap/vci.
  • The install script (~/.cargo/bin/vci with the clone in ~/.local/share/vci, or VCI_HOME): runs the clone's scripts/install.sh with VCI_REF set to the release's tag; without a clone, prints the command that installs it.
  • A release binary anywhere else: downloads vci-<target>.tar.gz and its SHA256SUMS-<target>, checks the SHA-256, and renames the new binary over the old one from a temporary file beside it. A directory it cannot write to is refused with the sudo command to run. --keep-old keeps the old binary as vci.old. Collectors in a share/vci beside it are not updated.
  • --check: only prints the installed and the latest version; exit 0 when current, 1 when there is an update. --version X.Y.Z: that release instead of the latest (not for Homebrew).
  • A lookup or download that fails is an error (exit 2). VCI_UPDATE_REPO and VCI_UPDATE_BASE_URL point it at other releases.
vci update --check || vci update

Signing key

vci signs with an SSH key. It uses the first of:

  1. --key PATH
  2. $VCI_SIGNING_KEY
  3. git config user.signingkey, when gpg.format = ssh

A GPG key is never used. A .pub path works when the private half is in ssh-agent, hardware keys included.

In GitHub Actions, CI can sign without a key (since 2.0): --oidc uses the job's OIDC token, an ephemeral key and a ten-minute Sigstore certificate, and .vci/identities.toml says which workflow runs are trusted. See keyless attestation.

Base ref

The base ref is the commit vci trusts: it reads the policy and the allowed signers from there, never from the code under test. vci uses the first of:

  1. --base-ref R
  2. $VCI_BASE_REF
  3. origin/$GITHUB_BASE_REF
  4. the first that exists of origin/HEAD, origin/main, origin/master, main, master

If none resolves, everything runs. vci plan warns when the base commit is HEAD or contains it, because then trust would come from the commit under test.

Environment variables

VariableMeaning
VCI_SIGNING_KEYSigning key path, when --key is not given
SIGSTORE_ID_TOKENA ready OIDC token for --oidc, instead of the GitHub Actions job's
VCI_BASE_REFBase ref, when --base-ref is not given
VCI_JOBSParallel pytest or go test processes in vci run (default: CPUs, up to 8). Rails files run one at a time: they share the test database.
VCI_JS_PLUGINPath of the @vci/vitest package (default: node_modules/@vci/vitest above the project)
VCI_PY_PLUGINThe py/pytest-plugin directory
VCI_RUBY_COLLECTORThe ruby/vci-collector directory
VCI_NODE, VCI_UV, VCI_GO, VCI_CARGO, VCI_RUBYBinary to use for each toolchain, instead of the one on PATH

The three collector paths are not needed with Homebrew or the GitHub Action, which set them up for you.

Looking at attestations directly

Attestations are ordinary git-meta values, so the git meta CLI can read them:

git meta get path:src/b.test.ts
git ls-remote origin refs/meta/main
