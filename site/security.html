How it works

What is signed, where it is stored, what CI checks before it skips anything, and what vci does not protect against.

The core rule: fail open

The default verdict for every test is RUN. A test is skipped only when one attestation passes every check. Any error, doubt or unrecognised behaviour means the test runs. Each candidate is checked inside an error boundary, so even a crash while checking is a failed check and never a skip.

What an attestation is

When vci run finishes a unit that passed and did nothing unobservable, it builds an in-toto statement and signs it with your SSH key (SSHSIG, namespace vci-attest) inside a DSSE envelope. The statement records:

  • inputs: every file (content hash), directory listing, symlink and probed-but-missing path the unit used;
  • global inputs: lockfiles, runner config and vci.toml;
  • externals: packages, modules, crates or gems, by name and version;
  • environment: a hash for each relevant variable, never its value;
  • toolchain: runner and language versions, OS and architecture;
  • identity: the repository (its root commit), the test id, the command line, the issue and expiry times.

Attestations are content-addressed by unit and inputs, not tied to a commit. They survive rebases and apply on every branch.

Where attestations live

vci keeps no storage format, database or server of its own. Each attestation is one git-meta value attached to the unit's path:

git meta get path:src/b.test.ts
  • Locally, values sit in git-meta's SQLite store at .git/git-meta.sqlite. Your index, HEAD and work tree are never touched.
  • They are exchanged on the remote's refs/meta/main by ordinary git push and fetch: vci push and vci fetch, or git meta push and git meta pull.
  • Two signers never write the same key, and merges keep keys added on either side.

Nothing in the store is trusted. Anyone with push access can write or delete metadata, exactly as with any other ref. A value that is deleted, overwritten, pruned or never fetched only means the unit runs. Only a correctly signed envelope for exactly this unit, repository, toolchain and inputs skips anything.

What vci plan checks

A file matching policy.never_skip runs. Otherwise each stored candidate is checked in this order, and the first candidate to pass every check means SKIP:

#CheckPasses when
1envelopeit parses as DSSE with the in-toto payload type
2signaturethe SSH signature covers the exact stored payload bytes
3signerthe key is in the base commit's allowed_signers, within its validity dates
4statementpredicate type and subject match
5expirynot expired, not issued in the future, lifetime within max_ttl
6repo, test id, adapter, argvall match this repository and unit
7toolchainlanguage and runner versions match, and OS and architecture satisfy policy.platform
8env-configthe [env] configuration at the base commit is the one attested under
9resultthe unit passed, untainted; declared inputs and waivers still match base policy
10global inputsevery global entry re-hashes to the same value in this checkout
11inputsevery file, symlink, directory listing and absence re-hashes to the same value
12externalsevery package is installed in exactly the attested version
13envevery hashed variable has the same value

vci explain prints the first failed check for each candidate.

When vci run refuses to attest

A unit gets no attestation, and so runs in CI, when vci cannot vouch for it:

  • it failed, or any of its tests was skipped;
  • it did something a collector cannot follow: a child process, network access, native code, enumerating the whole environment;
  • an input lies outside the repository;
  • an input changed during the run.

Each adapter has its own list; see test runners.

Threat model

Protected against

  • Forged or tampered attestations. The signature covers the exact payload bytes; one flipped byte fails.
  • Untrusted signers, including a pull request that adds its own key to .vci/allowed_signers. Trust and policy come only from the base commit.
  • Replay across repositories, test files, command lines, toolchains or env configurations, or after expiry.
  • Stale inputs. Every recorded input is re-hashed from CI's own checkout, including files that must still be absent.

Not protected against

  • A trusted signer lying, or a stolen signing key. An attestation proves who made a claim, not that the test ran. A signer can also under-declare inputs. Keep allowed_signers short, use hardware-backed keys, and set valid-before on entries.
  • Inputs the collectors cannot see: native addons, time, locale, randomness, hardware.
  • Test code that deliberately evades the collectors.
  • Malicious dependencies that match the lockfile. Packages are identified by version, not by file hashes.
  • A CI job whose base ref the pull request controls. Pass the base branch's commit, as the action does by default.

The backstop. Keep your default branch in policy.no_skip_refs (the vci init default). Every merge then gets a full run, which catches a false claim after the fact.
