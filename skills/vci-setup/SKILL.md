# vci setup: get one engineer ready

Set up vci for the person using this session, in the repository you are in. Do each step, report what you found, and ask before anything that changes something outside the working tree (a pull request, a shell profile).

1. **CLI.** Run `vci --version`. If it is missing or older than the version this repository's docs ask for, install or upgrade it with `brew install pandelisz/tap/vci` (or `brew upgrade pandelisz/tap/vci`); on Linux without Homebrew use the install script from the vci README.
2. **Repository.** If there is no `vci.toml` at the repository root, this repository is not set up for vci yet: say so, point at `vci init`, and stop. If there is a project-specific skill or doc for vci in this repository (for example a `vci` skill under `.claude/skills` or `.agents/skills`, or `docs/vci-quickstart.md`), follow it instead of the generic steps below.
3. **Trust.** Find the SSH key the person uses for GitHub (`ssh-add -L`, `~/.ssh/*.pub`, `gh api user/keys`) and check whether its public half is in `.vci/allowed_signers` on the default branch. If not, show the line to add (`<github-login> namespaces="vci-attest" <type> <key>`) and offer to open a pull request that appends it. Attestations are refused until that line is on the default branch.
4. **Environment.** Run `vci env` if this vci has it and report anything missing; otherwise follow the repository's docs. Never edit a shell profile without asking.
5. **Store.** Every vci command that reads the attestation store (`vci store info`, `plan`, `run`, `explain`, `fetch`, `push`, `prune`) runs `[store] token_command` and sends what it prints, the person's credential, to `[store] url`, both from this checkout's `vci.toml`. So first find the default branch (`git symbolic-ref --short refs/remotes/origin/HEAD`, such as `origin/main`) and run `git diff origin/<default-branch> -- :/vci.toml` as a command of its own (`:/` is the top level from any directory). If it fails, or changes `url` or `token_command` and the person did not make that change (someone else's branch or pull request), the checkout is unreviewed: put `VCI_STORE=git-meta` in front of every vci command from here on, steps 6 and 7 included, and say why. Then run `vci store info`, with that prefix in an unreviewed checkout; its output never holds a secret. On git-meta (the default) there is nothing to do. If the store is PostgreSQL or libSQL (Turso) and its credential comes from `[store] token_command`, the person must be signed in to that tool (`com login`, `op signin`) and allowed to read the secret (`com secrets get` reads an organization's secret for its admins only): ask them. If the command fails, never run it, or any other secret tool, yourself, not even with its output discarded: its standard error can hold the token. Tell the person what failed and the command vci names, and ask them to run it in their own terminal with its standard output discarded (`<command> > /dev/null`). vci 2.8.0's message leaves an argument holding `&`, `;`, `|` or a glob character unquoted, so with 2.8.0 give them the command from `vci.toml` with each such argument in single quotes. Never print, paste or store the token.
6. **Verify.** Run `vci plan --base-ref origin/<default-branch>` (with `VCI_STORE=git-meta` in front if step 5 found the checkout unreviewed) and explain the result in one paragraph: what would be skipped, what runs, and why.
7. **Next.** Tell the person the per-change loop: `vci run <the files or packages they touched>`, `vci plan`, `vci push` (on git-meta; a shared store has nothing to push, since `vci run` stored the attestations), then push the branch. In a checkout step 5 found unreviewed, each of them gets `VCI_STORE=git-meta` in front until the person has reviewed its `vci.toml`.
